High-Level Design (HLD)

System architecture, deployment zones, and component interactions

Complete System Architecture Diagram

🔑 Submission Pipeline Architecture

  • Async: Controller creates Submission(pending) → enqueues to BullMQ → returns 202
  • Back-pressure: Worker concurrency:5 — max 5 Judge0 calls simultaneously
  • Circuit Breaker: opossum opens after 50% failure (min 5 calls), 30s reset
  • Saga: Compensating transaction — any failure → status=error (no stuck pending)
  • Push: QueueEvents (Redis pub/sub) → Socket.IO → browser (no polling)
  • Idempotency: Idempotency-Key prevents duplicate submissions on retry

🗄️ Redis — 5 Distinct Roles

  • BullMQ backend: Queue storage — jobs/waiting/active/failed sets
  • Cache-aside: problem:{id} JSON blobs, TTL 300s
  • Token blocklist: token:{jwt} string, expireAt JWT.exp
  • Rate limiter: rl:{userId} ZSET, timestamp members, sliding window
  • Leaderboard: ZSET global (points) + per-problem (runtime ms)
  • Idempotency store: idemp:{uuid} JSON, TTL 24h

Internal module designs, state machines, and implementation details

Submission State Machine

pending
→

|
wrong
|
error
  • pending: Created on submit. Job queued. Status stored in MongoDB.
  • accepted: All hidden test cases pass. problemSolved $addToSet. ZINCRBY leaderboard.
  • wrong: ≥1 test case failed. testCasesPassed/total stored.
  • error: Judge0 failure, circuit open, compile error. Saga compensation.

Circuit Breaker State Machine

CLOSED
→
OPEN
→
HALF-OPEN
→
CLOSED
  • CLOSED: Normal. All calls pass to Judge0.
  • OPEN: After ≥50% failure (min 5 calls). Fails fast 30s. Zero Judge0 calls.
  • HALF-OPEN: One probe call. Success → CLOSED. Fail → OPEN again.
  • UnrecoverableError: BullMQ skips retries on circuit open → instant user feedback.

Sliding Window Rate Limiter (LLD)

// middleware/rateLimiter.middleware.js (core logic)
const createRateLimiter = ({ windowMs, max, keyPrefix, by='user' }) => async (req, res, next) => { const key = `${keyPrefix}:${by==='ip' ? req.ip : req.result?._id}`; const now = Date.now(); const windowStart = now - windowMs; try { const pipeline = redisClient.multi(); // 1. Remove timestamps older than window pipeline.zRemRangeByScore(key, '-inf', windowStart); // 2. Add current request timestamp pipeline.zAdd(key, [{score: now, value: `${now}-${Math.random()}`}]); // 3. Count requests in window pipeline.zCard(key); // 4. Auto-expire the key pipeline.expire(key, Math.ceil(windowMs / 1000)); const results = await pipeline.exec(); const count = results[2]; // zCard result if (count > max) { return res.status(429).json({ message: 'Too many requests', retryAfter: Math.ceil(windowMs / 1000) }); } } catch (_) { /* Fail-open */ } next(); };

Idempotency Middleware (LLD)

// middleware/idempotency.middleware.js
const idempotency = async (req, res, next) => { const key = req.headers['idempotency-key']; if (!key) return next(); // No key — proceed normally try { // Check for cached response const cached = await redisClient.get(`idemp:${key}`); if (cached) { const { statusCode, body } = JSON.parse(cached); return res.status(statusCode).json(body); // Replay } // Intercept response to cache it const originalJson = res.json.bind(res); res.json = (body) => { if (res.statusCode >= 200 && res.statusCode < 300) { redisClient.setEx(`idemp:${key}`, 86400, // 24h TTL JSON.stringify({ statusCode: res.statusCode, body }) ).catch(() => {}); } return originalJson(body); }; } catch (_) { /* Fail-open */ } next(); };

Leaderboard — Redis ZSET Operations (LLD)

// lib/leaderboard.js
const WEIGHT = { easy: 1, medium: 3, hard: 5 }; // Add solve points — idempotent via caller's alreadySolved check const addSolve = async (userId, difficulty) => { await redisClient.zIncrBy( 'leaderboard:global', WEIGHT[difficulty] || 1, userId.toString() ); }; // Record best runtime for per-problem leaderboard // ZADD LT = only update if new score is LESS than existing (keep minimum) const recordBestRuntime = async (problemId, userId, runtimeMs) => { await redisClient.zAdd( `leaderboard:problem:${problemId}`, { score: runtimeMs, value: userId.toString() }, { LT: true } // node-redis v4 option for ZADD LT ); }; // Get top N global — descending score (more points = higher rank) const getGlobalTop = async (n = 50) => { return redisClient.zRangeWithScores( 'leaderboard:global', 0, n - 1, { REV: true } ); }; // Get user rank and score const getMyStanding = async (userId) => { const rank = await redisClient.zRevRank('leaderboard:global', userId.toString()); const score = await redisClient.zScore('leaderboard:global', userId.toString()); const total = await redisClient.zCard('leaderboard:global'); return { rank, score, total, percentile: ((total-rank-1)/total*100).toFixed(1) }; };

Design Patterns Reference

All 12 patterns in ByteCode with file locations and rationale

Adapter

lib/judge0Adapter.js

Wraps raw Judge0 HTTP (submitBatch, poll, status map) behind execute(). Swap Judge0 = change one file only.

Circuit Breaker

lib/judge0Adapter.js (opossum)

50% failure threshold, min 5 calls, 30s reset. CLOSED/OPEN/HALF-OPEN. Integrated with UnrecoverableError.

Producer/Consumer

queues/ + workers/

Controller=producer, Worker=consumer. Decoupled via BullMQ+Redis. Back-pressure via concurrency:5.

Factory

auth.middleware.js + rateLimiter.middleware.js

createAuthMiddleware(role?) and createRateLimiter({opts}) return configured middleware. Zero duplication.

Cache-Aside

lib/cache.js

Read: check Redis, miss=DB+populate. Write: invalidate. Fail-open: Redis down = miss, DB fallback.

Saga / Compensating Tx

services/submissionService.js

3-step saga: evaluate, persist, leaderboard. Any failure = status:error saved before rethrow. No stuck pending.

Pub/Sub

socket.js (QueueEvents)

BullMQ QueueEvents subscribes to Redis channels. Worker publishes, socket server receives, pushes to browser.

Stateless + Blocklist

auth.controller + middleware

Stateless JWT + Redis blocklist on logout. Fail-open if Redis down. Token auto-expires via Redis TTL.

Repository / Service

controllers → services → models

Thin HTTP controllers, business logic in services, data access in models. Clean 3-tier separation.

Template Method

services/evaluation.js

evaluateTestcases() defines skeleton: format, call adapter, aggregate, determine status. Details in adapter.

Proxy (Interceptor)

idempotency.middleware.js

Wraps res.json() transparently. Controller calls normally, middleware intercepts, caches, calls original.

Observer

socket.js QueueEvents

queueEvents.on('completed'), .on('failed') — event-driven observer across processes via Redis pub/sub.

B2
Explain the Circuit Breaker pattern in detail: states and opossum config.SYSPAT
›
  • CLOSED: Normal. All calls go to Judge0.
  • OPEN: After 50% errors (min 5 calls). Fails immediately for 30s. No external calls.
  • HALF-OPEN: After 30s reset. One probe call. Success → CLOSED. Failure → OPEN again.
  • opossum config: timeout:20000, errorThresholdPercentage:50, resetTimeout:30000, volumeThreshold:5
  • Integration: Worker catches "breaker is open" → UnrecoverableError → instant job failure → Socket.IO error push in <1s
  • Without circuit breaker: each job retries up to 3x waiting 20s timeout each. User waits minutes.
B3
What is back-pressure and how does concurrency:5 implement it?SYSQUEUE
›
  • Back-pressure: Producer creates work faster than consumer can process. Without control: queue grows unbounded, system crashes.
  • concurrency:5: Worker processes at most 5 jobs simultaneously. Others wait in BullMQ queue (Redis).
  • Effect: Judge0 sees at most 5 concurrent batches regardless of how many users submit.
  • Why BullMQ: Jobs survive server restarts (Redis persists them). Back-pressure is durable, not lost on crash.
  • Tuning: Set concurrency based on Judge0 quota. Free: ~5. Paid: 20-50.
B4
Explain the Saga pattern in submissionService.js.SYSPAT
›
  • Step 1: evaluateTestcases() — if fails → catch: set status=error, save, throw
  • Step 2: submission.save() — if fails → same catch block handles it
  • Step 3: leaderboard.addSolve() + recordBestRuntime() — minor if fails (additive)
  • Compensating action: submission.status = 'error'; await submission.save().catch(() => {});
  • Why .catch(()=>{}) on the compensating save: If DB itself is down, silently skip. Original error is more important for retry logic. Throwing here shadows original error.
  • Result: No submission ever stuck at 'pending'. User always gets a final state.

What is idempotency and why does submit need it?SECSYS
›

  • Problem: Network glitch → browser retries POST /submit → two identical submissions → two Judge0 calls → duplicate leaderboard points.

C. Authentication & Security
C1
Why httpOnly cookies instead of localStorage for JWT?SEC
›
  • localStorage: Any JS on page (including XSS) can read it. XSS = token stolen = account takeover.
  • httpOnly: Inaccessible to JavaScript. XSS cannot read it.
  • secure:true: HTTPS only. Prevents MitM interception.
  • sameSite:none: Required for cross-origin (Vercel → Render). Must pair with secure:true (Chrome enforces).
  • withCredentials:true on Axios: Browser sends cookie cross-origin. Without this, cookie is blocked.
C2
How does the Redis token blocklist solve the JWT logout problem?SECCODE
›
  • JWT logout problem: JWTs are stateless. Once issued, valid until expiry. Logout on server has zero effect.
  • On logout: jwt.decode(token) → get payload.exp → Redis.set('token:'+token,'Blocked') with expireAt(payload.exp)
  • Auth middleware: After JWT verify → Redis.exists('token:'+token). If found → 401 Unauthorized.
  • Auto-cleanup: Key expires at JWT exp time. Storage bounded to active sessions.
  • Fail-open: Redis down → skip blocklist → JWT still validates. Minor security tradeoff for availability.
C3
Explain sliding window rate limiter vs fixed window.SECLLD
›
  • Fixed window problem: Allow 10/min. User sends 10 at 11:59, 10 more at 12:00 = 20 requests in 2 seconds. Boundary burst.
  • Sliding window: Always look at last N milliseconds from NOW. No window boundaries. True rate limiting.
  • Redis ZSET implementation: member=timestamp, score=timestamp. ZREMRANGEBYSCORE (prune old) → ZADD (add this) → ZCARD (count) → EXPIRE (cleanup). All pipelined in one round-trip.
  • Fail-open: Redis error → allow request. Availability over strict enforcement.
C4
Why does logout use jwt.decode() not jwt.verify()?CODESEC
›
  • jwt.verify(): Checks signature AND expiry. Throws TokenExpiredError on expired token.
  • Problem: User with expired token (browser cached old cookie) tries to logout. verify() throws → logout fails → user stuck.
  • jwt.decode(): Decodes payload WITHOUT verification. Always succeeds on structurally valid JWT.
  • Why safe: userMiddleware already verified the token before logout handler runs. decode() only needed for payload.exp to set Redis TTL correctly.
C5
What security vulnerabilities exist and how would you fix them?SEC
›

  • Submission ownership gap: GET /submissions/:id doesn't check ownership. Fix: check submission.userId.toString() === req.result._id.toString().
  • No helmet.js: Missing HTTP security headers. Add helmet() to Express app.

D. Redis & Data Structures
D1
Why Redis Sorted Sets for leaderboards? Why not MongoDB?DBSYS
›
  • MongoDB sort: O(N log N) collection scan + sort unless indexed. Slow with frequent writes + reads.
  • Redis ZSET: Always sorted by score. O(log N) insert (ZINCRBY). O(log N + M) range (ZREVRANGE). In-memory = microsecond reads.
  • ZREVRANK: User's rank in O(log N). Instant for millions of users.
  • ZADD LT: Add only if new score is less. Exactly what best-runtime leaderboard needs.
  • ZINCRBY: Atomic increment. No race conditions for score accumulation.
D2
Explain all Redis data structures used in ByteCode.DB
›
  • String: token:{jwt} (blocklist), idemp:{uuid} (idempotency), problem:{id} (cache JSON)
  • Sorted Set: rl:{userId} (rate-limiter sliding window), leaderboard:global (userId:points), leaderboard:problem:{pid} (userId:runtimeMs)
  • BullMQ internals (auto-managed): Lists (waiting jobs), Hashes (job data), Sets (job IDs), ZSETs (delayed/priority jobs)
  • Pub/Sub channels: QueueEvents subscribes to BullMQ's internal Redis pub/sub channels automatically.
D3
How does ZADD LT work for best-runtime per-problem leaderboard?DBCODE
›
  • ZADD LT: Updates score only if new value is LESS THAN existing. Keep minimum (fastest runtime).
  • User at 150ms submits 200ms → no update. Submits 100ms → updates to 100ms.
  • Ascending sort (ZRANGE, not ZREVRANGE): Lower score = faster = higher rank.
  • ZADD LT on every accept: Atomic. No need to check previous score in application code.
  • Per-problem key: leaderboard:problem:{problemId}. No cross-problem contamination.

G1
How do Socket.IO rooms work and why userId as room name?SYSCODE
›

WebSocket vs HTTP polling — when to use each?SYS
›

  • Socket.IO value-add: Rooms, auto-reconnect, fallback to long-polling through proxies, namespaces.

H1
Is ByteCode stateful or stateless? What are the implications?SYS
›

N. WebSockets & Socket.io Deep Dive
N1
What is the difference between WebSockets and HTTP Long Polling?SYS
›

HTTP Long Polling keeps a request open until the server has data, then closes it and immediately opens a new one. It has high header overhead. WebSockets establish a persistent, full-duplex TCP connection. After the initial HTTP handshake (101 Switching Protocols), data flows in both directions with minimal overhead (just 2-10 bytes per frame). Crucial for real-time chat where latency must be sub-100ms.

N2
Why use Socket.io instead of native WebSockets?NODE
›
  • Fallback: Automatically falls back to HTTP long-polling if WebSockets are blocked by a corporate proxy or firewall.
  • Reconnection: Built-in auto-reconnect logic if the connection drops.
  • Rooms & Namespaces: Trivially easy to broadcast to specific groups (e.g., `io.to(userId).emit(...)`). Native WS requires you to manually manage lists of connections.
  • Acknowledgments: Built-in support for request-response over WebSockets.
N3
How do you scale Socket.io across multiple Node.js instances?SYS
›

You cannot use sticky sessions alone because one user might connect to Instance A, and the person messaging them connects to Instance B. You must use a Redis Adapter. When Instance B wants to emit a message to a user on Instance A, it publishes the event to Redis. Instance A subscribes to Redis, receives the event, and pushes it through its local WebSocket to the user.

N4
Explain the heartbeat mechanism in Socket.io.SYS
›

To detect disconnected clients (e.g., user's laptop goes to sleep), Socket.io uses a ping/pong mechanism. The server sends a `ping` packet every `pingInterval` (default 25s). If the client doesn't respond with a `pong` within `pingTimeout` (default 20s), the server assumes the connection is dead and fires the `disconnect` event, cleaning up memory and updating online status.

N5
Write code to handle online user status using Socket.io.CODE
›
const userSocketMap = {}; // userId -> socketId io.on("connection", (socket) => { const userId = socket.handshake.query.userId; if (userId) { userSocketMap[userId] = socket.id; // Broadcast updated online users to everyone io.emit("getOnlineUsers", Object.keys(userSocketMap)); } socket.on("disconnect", () => { delete userSocketMap[userId]; io.emit("getOnlineUsers", Object.keys(userSocketMap)); }); });
N6
How do you secure Socket.io connections?SYS
›

Use middleware. `io.use((socket, next) => { ... })`. Extract the JWT token from `socket.handshake.auth.token` or cookies. Verify the token using `jwt.verify`. If valid, attach the decoded `userId` to the socket object and call `next()`. If invalid, call `next(new Error("Authentication error"))` which terminates the connection before it even starts.

N7
What happens if a user connects from two different tabs?SYS
›

Our `userSocketMap` currently maps `userId -> socketId`. If they open two tabs, the second tab overwrites the socket ID in the map. Messages will only go to the newest tab! Fix: Map `userId -> Set[socketId]`. When sending a message, iterate through the Set and emit to all active sockets for that user.

N8
How would you handle read receipts (seen status)?HLD
›

1. Receiver gets a message and views it. 2. Frontend emits a `markAsRead({ messageId, senderId })` event. 3. Server updates the message in MongoDB to `read: true`. 4. Server uses `io.to(senderId).emit('messageRead', messageId)`. 5. Sender's frontend updates the UI to show double blue ticks.

N9
Can WebSockets be load balanced?SYS
›

Yes, but you MUST use Session Affinity (Sticky Sessions) at the load balancer (e.g., NGINX, HAProxy, AWS ALB) if using Socket.io's HTTP long-polling fallback. Without sticky sessions, the HTTP handshake requests might hit different servers, breaking the upgrade process. If enforcing WebSocket-only transport, standard TCP load balancing works fine.

N10
What is the "Thundering Herd" problem on reconnect?SYS
›

If the server restarts, 10,000 WebSocket clients disconnect simultaneously. When the server comes back up, all 10,000 clients attempt to reconnect at the exact same millisecond, potentially crashing the server or DB. Socket.io solves this using "Randomized Exponential Backoff"—clients wait a random amount of time (e.g., 1s, then 2.5s, then 5s) before retrying.

P. Node.js & Express Architecture
P1
Explain the Node.js Event Loop.NODE
›

Node.js is single-threaded. The event loop handles asynchronous callbacks. Phases: 1. Timers (`setTimeout`). 2. I/O Callbacks (system errors). 3. Idle, prepare. 4. Poll (retrieve new I/O events like DB responses). 5. Check (`setImmediate`). 6. Close callbacks. Node delegates heavy I/O tasks to the OS kernel or the libuv thread pool, keeping the main thread unblocked.

P2
Why should you never write CPU-heavy code in Node.js?NODE
›

Because Node is single-threaded! If you write a `while` loop that takes 5 seconds to calculate prime numbers, the Event Loop is blocked. During those 5 seconds, Node cannot process ANY incoming HTTP requests, WebSocket events, or DB responses for ANY user. The server appears dead. CPU-heavy tasks must be sent to Worker Threads or a separate microservice (e.g., Go or Python).

P3
How do you scale a Node.js server to use all CPU cores?NODE
›

By default, Node uses 1 core. To use a 4-core CPU, use the native `cluster` module to fork 4 processes. Or better, use a process manager like **PM2** in cluster mode: `pm2 start server.js -i max`. PM2 acts as a local load balancer, routing incoming requests across all 4 Node.js instances automatically.

P4
What is Express middleware? Write one.CODE
›

Middleware are functions that have access to `req`, `res`, and `next`. They run sequentially. Used for logging, auth, parsing JSON.

const logger = (req, res, next) => { console.log(`${req.method} ${req.url}`); next(); // Pass control to next middleware }; app.use(logger);

P5
How do you handle global errors in Express?CODE
›

Define a middleware with EXACTLY 4 parameters at the very bottom of your middleware stack.

app.use((err, req, res, next) => { console.error(err.stack); res.status(500).json({ message: "Internal Server Error", error: process.env.NODE_ENV === "development" ? err.message : {} }); });

In async routes, you must wrap code in `try/catch` and call `next(error)` to trigger this, or use `express-async-errors` package.

P6
What is the difference between `res.json()` and `res.send()`?NODE
›

`res.send()` automatically detects the data type. If it's an object, it sets `Content-Type: application/json` and stringifies it. If it's a string, it sets `text/html`. `res.json()` strictly forces the formatting to JSON, even for non-objects. It's safer to use `res.json()` for APIs to guarantee the client always receives JSON.

P7
Explain Streams in Node.js.NODE
›

Streams handle reading/writing data chunk by chunk without loading everything into RAM. If you need to send a 1GB video file, `fs.readFileSync` will crash the server (Out of Memory). `fs.createReadStream().pipe(res)` reads a few KB at a time, sends it to the client, and frees the memory, keeping RAM usage perfectly flat regardless of file size.

P8
Why use `bcryptjs` over `bcrypt`?SYS
›

`bcrypt` relies on C++ bindings (`node-gyp`). It requires Python and a C++ compiler to be installed on the deployment server, which often fails in lightweight Docker containers. `bcryptjs` is written in 100% pure JavaScript. It is ~30% slower than native `bcrypt`, but guarantees cross-platform compatibility with zero installation headaches.

P9
How do you prevent brute-force login attacks?SYS
›

Use `express-rate-limit`. Apply it specifically to the `/login` route. Limit it to 5 requests per 15 minutes per IP. This prevents attackers from rapidly guessing passwords. For advanced protection, lock the specific user account for 30 minutes after 5 failed attempts (requires DB tracking), stopping distributed botnet attacks.

P10
How does Cookie-based auth compare to Header-based (Bearer)?SYS
›

Cookie-based (HttpOnly): Secure against XSS. Browser attaches it automatically to every request. Vulnerable to CSRF (requires SameSite attribute). Header-based (Authorization: Bearer ): Stored in localStorage or JS memory. Vulnerable to XSS. Immune to CSRF. We chose HttpOnly cookies for maximum XSS protection since chat apps are high targets for injected scripts.

Why use MongoDB over PostgreSQL for a chat application?DB
›

Q2
Explain Indexing in MongoDB and how you used it.DB
›

An index is a B-Tree data structure that stores a small portion of the collection's data in an easy-to-traverse form. Without an index, finding messages between User A and User B requires a "Collection Scan" (O(N) reading every message in the DB). By adding a Compound Index on `{ senderId: 1, receiverId: 1, createdAt: -1 }`, queries jump directly to the relevant messages in O(log N) time, drastically reducing CPU load.

›

You start a `session`, run multiple `save()` operations using `{ session }`, and then `session.commitTransaction()`. If any operation fails, `session.abortTransaction()` rolls back all changes, preventing partial updates.

Q7
What is a Replica Set and why is it important?SYS
›

A Replica Set is a group of mongod instances maintaining the same data. It provides High Availability (HA). One node is PRIMARY (receives writes). Others are SECONDARY (replicate data). If the Primary crashes, an automated election occurs, and a Secondary becomes the new Primary within seconds. It ensures your chat app doesn't go offline during hardware failures.

Q8

›

Q9

›

Q10
What is DB Sharding and when would you use it here?HLD
›

Sharding is Horizontal Scaling. A replica set scales reads, but ALL writes still go to the single Primary. When the chat app reaches tens of thousands of messages per second, the Primary's disk/CPU will bottleneck. Sharding splits the collection across multiple replica sets based on a Shard Key (e.g., `Hash(senderId)`). Writes are distributed across multiple servers.

R2
Explain the CAP Theorem in the context of this app.SYS
›

Consistency (C), Availability (A), Partition Tolerance (P). You can only pick 2. In distributed systems, P is mandatory (networks WILL fail). So we must choose between CP and AP. A chat app favors AP (Availability over Consistency). It's better for a user to see a message a millisecond late, or see slightly out-of-sync online statuses, than to have the app completely refuse connections to guarantee 100% data consistency (like a bank would).

›

Server A and Server B both connect to Redis. User 1 connects to A, User 2 connects to B. User 1 sends "Hi" to User 2. Server A realizes User 2 is not connected locally. Server A publishes the event to Redis: `PUBLISH "chat" '{"to":"user2","msg":"Hi"}'`. Server B, which is subscribed to "chat", receives the event, checks its local memory, finds User 2, and emits the message over its WebSocket.

R4

›

Databases (MongoDB) are terrible at serving large binary files (GridFS exists, but is slow). It handles storage, global distribution, and on-the-fly transformations (resizing, WebP compression), completely freeing up our Node server's bandwidth and CPU.

R5

›

The CDN caches our static assets (React JS, CSS, Images) in a Tokyo data center. The user downloads assets from Tokyo (10ms latency). Only dynamic API calls hit New York, vastly improving app load speed.

R6

›

It accepts port 443 (HTTPS), decrypts the SSL certificates, blocks malicious IP addresses, compresses responses with GZIP, and forwards clean HTTP traffic to Node.js on port 3000. It acts as a shield and performance booster.

R7

›

Our app is a Monolith: auth, messaging, and profile logic are in one codebase. It's easy to deploy and debug. Microservices split these into separate deployed apps (Auth Service, Chat Service, Media Service) communicating via APIs/gRPC. Microservices allow independent scaling (e.g., scaling Chat without scaling Auth) and polyglot teams (Auth in Go, Chat in Node), but add immense deployment complexity and network latency.

R8

›

R9

V. Security Best Practices
V1
Explain CSRF and how to prevent it.SYS
›

Cross-Site Request Forgery. If a user is logged into our app, and visits `malicious.com`, that site can execute a hidden POST request to `our-app.com/delete-account`. The browser automatically attaches our HttpOnly auth cookie! Prevent it by setting the cookie attribute `SameSite=Strict` or `Lax`, which tells the browser to NOT send cookies if the request originates from a different domain.

V2
What is CORS?SYS
›

Cross-Origin Resource Sharing. By default, browsers block JS on `localhost:5173` from making API calls to `localhost:5001`. The backend MUST return specific headers (`Access-Control-Allow-Origin`). We use the `cors` npm package in Express to manage this, allowing our specific frontend URL to communicate with our API.

V3
How do you prevent SQL/NoSQL Injection?SYS
›

In NoSQL, attackers inject MongoDB operators via JSON payload. E.g., `password: { $gt: "" }`. If we don't sanitize `req.body`, Mongoose might interpret this as "find a user where password is greater than empty string" and bypass auth. Prevent it using `express-mongo-sanitize` which recursively removes any keys starting with `$` or `.` from the request body.

V4

›

Helmet is a middleware that sets 14 different HTTP security headers. Examples: `X-XSS-Protection` (blocks cross-site scripting), `X-Frame-Options` (prevents clickjacking by stopping your site from being embedded in an iframe), and `Strict-Transport-Security` (enforces HTTPS).

V5
What is a timing attack and how do you prevent it?SYS
›

If comparing strings character by character (e.g., verifying a secret token), standard `==` stops checking as soon as it finds a mismatch. An attacker can measure the time taken to know if they guessed the first character right. Prevent this using `crypto.timingSafeEqual`, which takes the exact same amount of CPU time regardless of where the mismatch occurs.
