Overview

🏗️ Project Overview & Architecture (Q1–Q18)

Q1 What is ByteCode? Give a 60-second elevator pitch.

ByteCode is a full-stack LeetCode-style competitive programming platform. Users solve DSA problems in an in-browser Monaco editor (C++, Java, JavaScript), run code against visible test cases instantly, and submit against hidden test cases asynchronously. The submission pipeline is a fault-tolerant async queue: the controller enqueues the job, a BullMQ worker evaluates it via Judge0, and the verdict is pushed back over Socket.io — no polling. It also features Redis ZSET leaderboards, a threaded discussion forum, an AI coding tutor via OpenRouter, video editorials via Cloudinary, and a full admin panel. The system implements 10+ production-grade patterns: circuit breaker, cache-aside, sliding-window rate limiter, idempotency, saga/compensating transactions, and fail-open resilience.

Q2 Why did you build this instead of just using LeetCode?

This project was a vehicle to implement real backend patterns. While LeetCode is a product, ByteCode is an engineering showcase. Every pattern — job queue, circuit breaker, cache-aside, rate limiter — is small, isolated, and defensible. It demonstrates that I can build systems beyond CRUD: an asynchronous pipeline with back-pressure, real-time push, and fault tolerance.

Q3 Walk me through the complete submission flow, from button click to verdict on screen.

1. User clicks Submit → browser POSTs to /submission/submit/:id with code + language.
2. Request passes through: userMiddleware (JWT verify + Redis blocklist check) → submitLimiter (sliding-window rate limit) → idempotency (check Idempotency-Key header).
3. Controller creates a Submission document with status: "pending" in MongoDB, increments totalSubmissions on the Problem, invalidates cache, then calls enqueueSubmission().
4. BullMQ adds a job to the submissions queue with jobId = submissionId (for idempotent dedup) and returns. Controller responds 202 Accepted.
5. The BullMQ Worker (concurrency: 5) picks the job, calls processSubmission().
6. Service loads the Submission and Problem from MongoDB, calls evaluateTestcases() with hidden test cases.
7. evaluateTestcases() builds a Judge0 batch via judge0Adapter.execute(), which passes through the opossum circuit breaker.
8. If the breaker is closed, raw HTTP calls go to Judge0 RapidAPI: POST batch → poll GET until all status_ids > 2 (up to 30 attempts).
9. Results are parsed: count passed test cases, sum runtime, track max memory, determine status (accepted/wrong/error).
10. Verdict is saved to the Submission document. If accepted and first solve, User.problemSolved is updated with $addToSet and leaderboard scores are updated.
11. Worker returns the result object. BullMQ emits a completed event via QueueEvents.
12. socket.js listens to QueueEvents, parses the return value, and does io.to(userId).emit("submission:result", result).
13. The browser's Socket.io client receives the event and updates the UI.

Q4 Why is the submission flow asynchronous instead of a simple synchronous request-response?

Judge0 is an external API that takes 2–10+ seconds per evaluation. A synchronous flow would: (a) block the Express event loop, reducing throughput to near-zero under load; (b) tie up HTTP connections during the slow external call; (c) risk timeouts on proxies/load balancers (e.g. Render's 30s timeout); (d) provide no natural place for retry/backoff if Judge0 fails. The async queue decouples the acceptance of a submission from its evaluation, so the API stays responsive (202 in ~50ms), back-pressure is controlled (concurrency: 5), and retries are automatic (3 attempts with exponential backoff).

Q5 What's the difference between "Run" and "Submit"?

Run tests against visible test cases, is synchronous (the controller calls evaluateTestcases() directly and waits), and does NOT create a Submission record — it's ephemeral feedback. Submit tests against hidden test cases, is asynchronous (enqueued via BullMQ), creates a persistent Submission document, updates the leaderboard on acceptance, and the result is pushed via Socket.io. Both share the same evaluateTestcases() Template Method — they only differ in which test cases are passed and what happens with the result.

Q6 Explain the layered architecture of the backend.

The backend follows a Controller → Service → Repository layering:
Controllers handle HTTP concerns: parse request, validate input, call service, format response.
Services (submissionService.js, evaluation.js) contain business logic: orchestrate evaluation, persist verdicts, update leaderboards.
Lib (cache.js, leaderboard.js, judge0Adapter.js) are infrastructure adapters — they abstract Redis, Judge0, etc.
Models are Mongoose schemas, acting as the repository/data-access layer.
Middleware handles cross-cutting concerns: auth, rate limiting, idempotency.
This separation means you can swap MongoDB for PostgreSQL by changing models, or swap Judge0 for a self-hosted judge by changing only the adapter.

Q7 Why Express 5 specifically?

Express 5 adds native support for async error handling in route handlers (rejected promises are automatically forwarded to the error handler without needing try/catch wrappers or express-async-errors). It also removes deprecated APIs and improves path routing. Since this is a greenfield project, there's no legacy compatibility concern.

Q9 What is the "fail-open" philosophy and where is it applied?

Fail-open means: if a non-critical dependency (Redis) is unavailable, allow the request to proceed rather than crashing. Applied in: cache (miss → query DB), rate limiter (skip check → allow request), token blocklist (skip check → JWT is still valid by signature), leaderboard (return empty array). The philosophy is availability > strictness. MongoDB is the only hard dependency — the app can't function without its data.

Q10 How does the project handle two different deployment targets (Vercel vs Render)?

Two separate entry points: server.js exports a serverless function handler for Vercel (no HTTP server, no Socket.io — just the Express app behind a ready-promise). index.js creates an http.createServer, attaches Socket.io, starts the BullMQ worker in-process, and runs a keep-alive timer for Render/Railway. The same app.js (Express middleware + routes) is shared by both.

Q11 What external services does the project depend on?
  • Judge0 (RapidAPI) — code execution engine
  • MongoDB Atlas — primary database
  • Redis (hosted) — caching, queues, leaderboard, rate limiting, blocklist, idempotency
  • Cloudinary — video hosting and signed uploads
  • OpenRouter — LLM API gateway (routes to models like Llama 3.1)
  • Vercel — frontend hosting (static SPA)
  • Render — backend hosting (web service + in-process worker)
Q12 What is RUN_WORKER_IN_PROCESS and why does it exist?

On Render's free tier, you get one web service. A separate BullMQ worker would need a paid worker service. When RUN_WORKER_IN_PROCESS=true, the index.js entry point calls createSubmissionWorker() inside the same Node.js process as the web server. This is a pragmatic cost optimization. For production at scale, you'd set it to false and run npm run worker as a separate service, scaled independently.

Q13 Explain the keep-alive mechanism. Why is it needed?

Render's free tier spins down a service after ~15 minutes of no inbound traffic. This would kill the in-process BullMQ worker. The keep-alive has two layers: (1) In-app self-ping: setInterval every 14 minutes hitting /health via the RENDER_EXTERNAL_URL — only during active hours (08:30–21:30 IST) to save free instance-hours overnight. (2) GitHub Actions cron: keep-alive.yml runs every 10 minutes during the same IST window, pinging from GitHub's runners — this can also wake a sleeping service (the in-app ping can't do that since the process itself is asleep).

Q14 What does the render.yaml file do?

It's a Render Blueprint — Infrastructure as Code. When you connect the repo to Render and select "Blueprint", it reads this YAML and automatically creates the web service with the correct build/start commands, region (Singapore), plan (free), health check path, and environment variable groups. Secrets like DB_CONNECT_STRING are marked sync: false so they're entered in the dashboard, never committed. It's the equivalent of a Terraform/CloudFormation file for Render.

Q15 Why CommonJS (require) in the backend and ESM (import) in the frontend?

The frontend uses Vite which is ESM-native. The backend uses "type": "commonjs" because some dependencies (notably BullMQ's Worker, opossum, older Mongoose patterns) have historically had smoother CJS support. Express 5 works with both. This is a pragmatic choice — not ideological.

Q16 How is CORS configured and why is credentials: true critical?

CORS is configured in origins.config.js with three allowed origins: FRONTEND_URL env var, a regex for localhost (any port), and the Vercel production URL. credentials: true is required because auth uses httpOnly cookies. Without it, the browser won't send or accept cookies on cross-origin requests. Both Express CORS middleware and Socket.io's CORS config use the same origins array.

Q17 What's the health endpoint for and who calls it?

GET /health returns { status: "ok" }. It's called by: (1) Render's health check system (configured in render.yaml as healthCheckPath) to verify the service is ready; (2) the in-app keep-alive timer; (3) the GitHub Actions cron workflow. It's intentionally lightweight — no DB query, no Redis call — just a 200 OK to prove the process is alive.

Q18 What happens at server startup? Walk through index.js.

1. Load .env via dotenv. 2. Import app (Express), configs, socket module, worker factory. 3. Create http.createServer(app) and call initSocket(server) to attach Socket.io + QueueEvents listener. 4. In an async IIFE: connect to MongoDB (required — fails loudly), connect to Redis (optional — continues without it). 5. Start listening on PORT. 6. If RUN_WORKER_IN_PROCESS=true, call createSubmissionWorker(). 7. Call startKeepAlive() to begin the self-ping timer if on Render.

Auth & Security

🔐 Authentication & Authorization (Q19–Q40)

Q19 How does authentication work end-to-end?

On login/register, the server hashes the password with bcrypt (salt rounds: 10), creates a JWT containing { _id, emailId, role } signed with JWT_KEY (1-hour expiry), and sets it as an httpOnly, secure, sameSite=none cookie. On every subsequent request, the auth middleware extracts the cookie, verifies the JWT signature + expiry, checks the Redis token blocklist, loads the user from MongoDB, and attaches req.result. On logout, the token is added to a Redis blocklist with TTL = JWT expiry time, and the cookie is cleared (maxAge: 0).

Q20 Why httpOnly cookies instead of localStorage?

httpOnly means JavaScript cannot read the cookie via document.cookie — this prevents XSS attacks from stealing the token. If you store JWT in localStorage, any XSS vulnerability can exfiltrate it. With httpOnly cookies, even if an attacker injects script, they can't access the token. The cookie is automatically sent by the browser on every request, so the frontend doesn't need to manually manage authorization headers.

Q21 Explain sameSite: "none" and secure: true. Why are both needed?

The frontend (Vercel: byte-code-frontend.vercel.app) and backend (Render: *.onrender.com) are on different domains. Browsers block cross-origin cookies by default. sameSite: "none" tells the browser to send the cookie on cross-origin requests. But browsers require secure: true (HTTPS only) whenever sameSite: "none" is used — this is a security requirement to prevent MITM attacks. Both flags together enable cross-origin cookie auth over HTTPS.

Q22 What is the token blocklist and why not just delete the JWT on logout?

JWTs are stateless — the server doesn't store them. You can't "delete" a JWT from the server side; it's valid until it expires. The blocklist is a Redis SET: on logout, token:{jwt} → "Blocked" with TTL = remaining JWT lifetime. On every auth check, the middleware calls redisClient.exists() to see if the token is blocked. This gives you the scalability benefits of stateless JWT with the security of revocable sessions.

Q23 What happens if Redis is down during auth? Can users still log in?

Yes — the blocklist check is wrapped in a try/catch that fails open. If Redis is unreachable, the middleware logs a warning and skips the blocklist check. The JWT signature + expiry are still verified (that's crypto, no external dependency). Users who logged out while Redis was up might have their old tokens still work briefly — but the JWT's 1-hour expiry limits the exposure window. This is the availability-over-strictness tradeoff.

Q24 Explain the Factory Pattern in createAuthMiddleware().

Instead of having two near-identical middleware files (one checking role === 'admin', one not), there's a single factory function: createAuthMiddleware(requiredRole). It returns a middleware closure. user.middleware.js exports createAuthMiddleware() (no role = any user). admin.middleware.js exports createAuthMiddleware("admin"). This eliminates code duplication — the only difference between user and admin auth is a single if check on payload.role.

Q25 Why is the role checked from the JWT payload rather than the DB user object?

The JWT is signed server-side with a secret key, so payload.role is tamper-proof. An attacker can't modify the role in the JWT without invalidating the signature. Checking from the JWT avoids an extra DB read. However, the middleware also does User.findById(_id) to verify the user still exists — this catches deleted accounts. The role in the JWT is trusted because it was set at sign time by the server.

Q26 What's the bcrypt salt rounds (cost factor) and why 10?

Salt rounds of 10 means 2^10 = 1024 iterations of the hashing function. This takes ~100ms on modern hardware, which is negligible for a login request but makes brute-force attacks impractical (~10 hashes/second). Higher values (12, 14) are more secure but slower. 10 is the widely-accepted default balancing security and performance.

Q27 How does jwt.verify() differ from jwt.decode()?

jwt.verify() checks the signature using the secret key AND checks expiry — it throws if invalid. jwt.decode() just base64-decodes the payload without any verification. In the codebase, verify() is used in auth middleware (security-critical), while decode() is used in logout to extract the expiry time for the blocklist TTL — the token's content doesn't need to be trusted there, just its expiry field.

Q28 Why is emailId marked as immutable: true in the User schema?

Mongoose's immutable prevents the field from being changed after creation via .save() or findOneAndUpdate(). This is important because the email is a unique identifier used in JWT payloads and throughout the system. Allowing email changes could break references or create security issues (e.g., someone changing to another person's email).

Q29 What's the user deletion cascade? What happens when an admin deletes a user?

The User schema has a post('findOneAndDelete') Mongoose hook that automatically deletes all submissions for that user: mongoose.model('submission').deleteMany({ userId: userInfo._id }). This is a cascading delete — it ensures no orphaned submission records remain. The hook fires after any findByIdAndDelete() or findOneAndDelete() call.

Q30 How does the admin prevent deleting themselves?

In adminDeleteUser, there's a check: if (id === req.result._id.toString()) — if the target user ID matches the admin's own ID, it returns 400 "You cannot delete your own admin account." This prevents accidental self-removal that would lock out administration.

Q31 What rate limits are applied to auth routes?

Login: 8 requests per 60 seconds per IP. Register: 5 requests per 60 seconds per IP. Both use the createRateLimiter() factory with by: "ip" (since users aren't authenticated yet). This slows brute-force password attacks and registration spam.

Q32 Why rate-limit login by IP rather than by email?

At the login endpoint, you don't yet know if the email is valid (it might not exist in the DB). Rate limiting by IP catches attackers trying multiple emails. Rate limiting by email could also be useful (prevents credential stuffing against a known email), but IP-based is the simpler first defense that catches the broadest set of attacks.

Q33 What's the JWT expiry and why 1 hour?

The JWT expires in 1 hour (expiresIn: "1h"). This balances UX (user doesn't need to re-login every 5 minutes) with security (a stolen/leaked token has limited usefulness). Combined with the Redis blocklist for immediate revocation on logout, 1 hour is a reasonable window. Some apps use refresh tokens for longer sessions — this project keeps it simple with a single short-lived token.

Q34 How does the frontend check if a user is still authenticated on page reload?

In App.jsx, a useEffect on mount dispatches checkAuth() — a Redux Toolkit createAsyncThunk that GETs /user/check. The cookie is sent automatically. If valid, the backend returns the user object; if not, it returns 401. The slice treats a 401 as "no session" (sets isAuthenticated: false, error: null) rather than showing an error — this is expected on first visit.

Q35 What's the validate() function doing for registration?

It checks that firstName, emailId, and password are all present in the request body (mandatory fields). Then it uses the validator library's isEmail() to verify the email format. The strong password check is commented out for development convenience but would be enabled in production.

Q36 Why does the admin register route sit behind adminMiddleware?

Only an existing admin can create another admin. This prevents privilege escalation — a regular user can't POST to /user/admin/register because the middleware checks payload.role === "admin" from the JWT. The first admin must be created by directly inserting into the database or temporarily disabling the middleware.

Q37 What security vulnerability did the original admin register have (Bug 5)?

The original code never set req.body.role = 'admin', so calling the admin register route still created a user with role "user" (the schema default). The fix explicitly forces req.body.role = 'admin' before calling User.create(). The route is already admin-protected, so only admins can reach it — the bug was that it didn't actually grant admin privileges.

Q38 How does req.result flow through the middleware chain?

The auth middleware calls User.findById() and sets req.result = result (the full Mongoose user document). Every downstream middleware and controller can then access req.result._id, req.result.role, req.result.firstName, etc. This avoids redundant DB lookups — the user is fetched once per request.

Q39 Why does the cookie have path: "/"?

path: "/" means the cookie is sent with every request to the backend, regardless of the URL path. Without it, the browser might scope the cookie to the path of the response that set it. Since auth is needed on /user/*, /problem/*, /submission/*, etc., the cookie must be available on all paths.

Q40 What happens if someone tampers with the JWT payload (e.g., changes role to admin)?

jwt.verify() will throw an JsonWebTokenError because the signature no longer matches the payload. JWT signatures use HMAC-SHA256 with the secret key. Changing even one character in the payload invalidates the signature. The request is rejected with 401. This is why the JWT secret must never be leaked.

Database

🗃️ MongoDB & Mongoose (Q41–Q60)

Q41 Why MongoDB over a relational database like PostgreSQL?

Problems have variable-length arrays (test cases, start code per language, reference solutions per language, tags) that map naturally to embedded documents in MongoDB. In SQL, these would require multiple join tables. The data is mostly read-heavy with simple query patterns (no complex JOINs needed). MongoDB Atlas provides a generous free tier for hosting. The schema flexibility also allows rapid iteration during development.

Q42 Walk me through all 5 Mongoose models and their relationships.

User — core identity (firstName, emailId, password, role, problemSolved[ObjectId→Problem]).
Problem — DSA problem (title, description, difficulty, tags, visibleTestCases[], hiddenTestCases[], startCode[], referenceSolution[], problemCreator→User).
Submission — one code attempt (userId→User, problemId→Problem, code, language, status, runtime, memory, testCasesPassed/Total). Compound index on {userId:1, problemId:1}.
Discussion — threaded comment (problemId→Problem, userId→User, text, parentId→Discussion (self-ref), upvotes[ObjectId→User]).
SolutionVideo — Cloudinary video (problemId→Problem, userId→User, cloudinaryPublicId, secureUrl, duration).

Q43 Why is there a compound index on {userId:1, problemId:1} in Submission?

The most common queries are: "all submissions by this user for this problem" (submission history on the problem page) and "accepted submissions by this user" (for profile stats). The compound index lets MongoDB satisfy both queries efficiently with an index scan instead of a collection scan. The userId prefix means queries on just userId also benefit (leftmost prefix rule).

Q44 Explain the $addToSet operation used for problemSolved.

$addToSet adds a value to an array only if it doesn't already exist. When a user gets an accepted submission, the service does User.findByIdAndUpdate(userId, { $addToSet: { problemSolved: problemId } }). This is idempotent — submitting the same problem multiple times won't create duplicates. It's an atomic operation, so no race conditions between concurrent submissions.

Q45 What is the Mongoose post('findOneAndDelete') hook and why use it?

It's a post middleware that runs after a findOneAndDelete() completes. In the User model, it deletes all submissions belonging to the deleted user: mongoose.model('submission').deleteMany({ userId: userInfo._id }). This is a cascading delete that prevents orphaned data. Using a hook keeps the cleanup logic co-located with the model rather than scattered across controllers.

Q46 How does the profile stats endpoint use MongoDB aggregation?

The getProfileStats controller runs two aggregation pipelines: (1) Problem.aggregate([{$group: {_id: "$difficulty", count: {$sum: 1}}}]) counts total problems by difficulty. (2) Submission.aggregate([{$match: {userId, status:'accepted'}}, {$group: {_id: "$problemId"}}, {$lookup: {from: 'problems', ...}}, {$facet: {byDifficulty: [...], byTag: [...]}}]) counts unique solved problems grouped by difficulty and by tag. It also fetches the last 10 submissions and a year-long activity calendar using $dateToString.

Q47 What's the $facet stage in aggregation?

$facet runs multiple aggregation sub-pipelines on the same input documents in parallel, outputting each as a named field. In the profile stats, it produces byDifficulty (grouped by difficulty) and byTag (unwound and grouped by tag) from the same set of solved problems — in a single aggregation call instead of two separate queries. This reduces database round trips.

Q48 Why embed test cases as arrays instead of a separate collection?

Test cases are always accessed with their problem — you never query test cases independently. Embedding avoids a JOIN ($lookup) on every problem read. The data size is small (a few KB of input/output strings). This follows MongoDB's rule of thumb: embed when the child data is always accessed with the parent and doesn't grow unboundedly.

Q49 How does populate() work and where is it used?

Mongoose populate() replaces an ObjectId reference with the actual document from the referenced collection (like a client-side JOIN). Used in: submissions list (populate('userId', 'firstName role') and populate('problemId', 'title')), discussions (populate('userId', 'firstName')), and solved problems (populate({path: 'problemSolved', select: '_id title difficulty tags'})). The select parameter limits which fields are fetched — important for performance.

Q50 What's the enum validator on the difficulty field?

enum: ['easy', 'medium', 'hard'] restricts the difficulty field to exactly those three values. Mongoose will throw a validation error if you try to set it to anything else. Similarly, submission language is enum: ['javascript', 'c++', 'java'], user role is enum: ['user', 'admin'], and submission status is enum: ['pending', 'accepted', 'wrong', 'error'].

Q51 Why timestamps: true on schemas?

It automatically adds createdAt and updatedAt fields managed by Mongoose. createdAt is used for sorting submissions chronologically (sort({ createdAt: -1 })), the activity calendar ($dateToString on createdAt), and showing when discussions were posted. updatedAt tracks the last modification of any document.

Q52 How are tags implemented and what's the enum restriction?

Tags is an array of strings with enum validation covering 16 categories: array, linkedList, graph, dp, tree, string, greedy, stack, queue, math, bitManipulation, backtracking, twoPointers, binarySearch, heap, premium, video. This prevents typos and ensures consistency across all problems. The frontend uses these exact values for filtering.

Q53 How does the discussion threading work with parentId?

The Discussion model has a parentId field that references itself (self-referential). Top-level comments have parentId: null. Replies set parentId to the comment they're replying to. The server returns all comments flat (sorted by createdAt); the client nests them by matching parentId to build the thread tree. This avoids recursive queries on the server.

Q54 How are upvotes implemented atomically?

The toggleUpvote controller checks if the user already upvoted using comment.upvotes.some(). Then it uses an atomic MongoDB update: $pull (remove) if already upvoted, $addToSet (add without duplicates) if not. This is a single atomic operation, so concurrent clicks can't double-add or double-remove a user's upvote.

Q55 What does select() do in Mongoose queries?

.select('_id title difficulty tags') performs a projection — only those fields are fetched from MongoDB. This reduces network transfer and memory usage. For example, getAllProblem doesn't fetch test cases, start code, or reference solutions — just the metadata needed for the listing page.

Q56 Why is emailId both unique and lowercase: true?

unique creates a unique index so two users can't register with the same email. lowercase: true normalizes the email before saving, preventing "John@Gmail.com" and "john@gmail.com" from being treated as different users. trim: true removes leading/trailing whitespace.

Q57 How does pagination work in getAllSubmissions?

Uses skip/limit pagination: page and limit come from query params. skip = (page - 1) * limit. The query sorts by createdAt: -1 (newest first), skips the first N, and limits to the page size. It also returns totalPages and totalSubmissions via countDocuments(). This is simple but has O(N) skip cost for deep pages — cursor-based pagination would be better at scale.

Q58 What's the difference between findByIdAndUpdate vs save()?

findByIdAndUpdate is a single atomic DB operation, bypasses some middleware. save() loads the document into memory, applies changes, then writes back — it runs validators and middleware hooks. In submissionService.js, submission.save() is used because the document is already loaded and multiple fields need updating. For simple atomic updates like $addToSet, findByIdAndUpdate is preferred.

Q59 How does the problem creation flow validate the reference solution?

Before saving a problem, the controller submits each reference solution to Judge0 against the visible test cases. For each language, it builds a batch, submits to Judge0, polls for results. If any test case doesn't return status_id: 3 (Accepted), it responds 400 — the problem isn't created. This ensures the reference solution is correct before students see it.

Q60 Why does runValidators: true matter in findByIdAndUpdate?

By default, Mongoose findByIdAndUpdate skips schema validators (enum, min, max, etc.). runValidators: true forces them to run. In updateProblem, this ensures the updated difficulty is still one of ['easy', 'medium', 'hard'], tags are valid enum values, etc. Without it, invalid data could sneak into the database.

Redis

⚡ Redis — Cache, Rate Limit, Blocklist (Q61–Q82)

Q61 How does the cache-aside pattern work in this project?

Read path: Controller calls cacheGet(key). If Redis returns data → serve it (cache hit). If null → query MongoDB → call cacheSet(key, data, 300) → serve the DB result. Write path: After any create/update/delete on a problem, call cacheDel("problems:all", "problem:{id}") to invalidate. This is the textbook cache-aside (lazy-loading) pattern. TTL is 300 seconds (5 minutes) as a safety net against stale data.

Q62 Why cache-aside instead of write-through or write-behind?

Write-through updates cache on every write — adds latency to writes and caches data that may never be read. Write-behind queues writes — adds complexity and risks data loss. Cache-aside is the simplest: only cache what's actually read, invalidate on write. For a system with moderate write frequency and frequent reads (problem listing page), cache-aside is the best tradeoff between complexity and effectiveness.

Q63 What are the cache keys and what do they store?

problems:all — JSON array of all problems (title, difficulty, tags, totalSubmissions). problem:{id} — JSON of a single problem's detail (with video info merged in). Both are serialized with JSON.stringify() and deserialized with JSON.parse() via the cacheGet/cacheSet helpers in lib/cache.js.

Q64 Explain the sliding-window rate limiter implementation.

Uses a Redis Sorted Set (ZSET) per user/IP. Each request adds a member scored by the current timestamp. The algorithm: (1) ZREMRANGEBYSCORE removes entries older than the window. (2) ZADD adds the current request with timestamp as score. (3) ZCARD counts remaining entries. (4) EXPIRE sets TTL on the key. All four commands are pipelined in a multi() (transaction). If count > max, return 429 with Retry-After header.

Q65 Why is a sliding window better than a fixed window?

A fixed window (e.g., "10 requests per minute starting at :00") has a burst-at-boundary problem: a user can make 10 requests at :59 and 10 more at :00 — 20 requests in 2 seconds. A sliding window counts requests in the last 60 seconds from now, so the limit is always enforced consistently. The ZSET approach gives true sliding-window behavior with O(log N) operations.

Q66 Why is Math.random() appended to the ZSET member?

ZSET members must be unique. If two requests arrive at the exact same millisecond, they'd have the same score AND same value, causing one to be silently dropped. Appending -${Math.random()} to the timestamp ensures uniqueness. This is a subtle but critical detail for correctness.

Q67 What rate limits exist in the system?

Login: 8/min per IP. Register: 5/min per IP. Submit: 10/min per user. Run: 20/min per user. Auth routes use IP-based limiting (user isn't identified yet). Submission routes use user-based limiting (after auth middleware provides req.result).

Q68 What's the multi() call doing in the rate limiter?

multi() creates a Redis pipeline — all four commands (ZREMRANGEBYSCORE, ZADD, ZCARD, EXPIRE) are sent in a single round-trip, reducing network latency. Note: in node-redis, multi() is a transaction (MULTI/EXEC), meaning all commands execute atomically. No other client can see the intermediate state.

Q69 How does the idempotency middleware prevent duplicate submissions?

The client sends a unique Idempotency-Key header per action. The middleware checks Redis for idemp:{key}. If found, it replays the cached response (status code + body) without running the handler. If not found, it wraps res.json() to capture the response — on success (2xx), it stores the response in Redis with 24-hour TTL. So a network retry or double-click gets the exact same response without creating a duplicate submission.

Q70 How does the idempotency middleware intercept res.json()?

It saves a reference to the original: const originalJson = res.json.bind(res). Then it replaces res.json with a wrapper that: (1) stores the response in Redis if status is 2xx, (2) calls the original originalJson(body). This is the decorator pattern applied to Express response methods — non-invasive, doesn't require changes to controllers.

Q71 What's the TTL for each Redis use case and why?

Cache: 300s — balances freshness with DB load reduction. Blocklist: JWT expiry time — no need to keep it after the JWT would naturally expire. Rate limit: Math.ceil(windowMs / 1000) — auto-cleanup matches the rate limit window. Idempotency: 24 hours — covers network retries and user coming back to retry. Leaderboard: No TTL — persistent ranking data.

Q72 How does redisClient.expireAt() differ from expire()?

expire(key, seconds) sets a relative TTL. expireAt(key, unixTimestamp) sets an absolute expiry time. The blocklist uses expireAt with payload.exp (the JWT's expiry as a Unix timestamp) — so the blocklist entry dies at exactly the same moment the JWT would naturally become invalid, regardless of when the logout happened.

Q73 Why two different Redis client libraries (node-redis vs ioredis)?

BullMQ requires ioredis — it's a hard dependency. BullMQ needs maxRetriesPerRequest: null to handle long-blocking operations (BRPOPLPUSH for queue consumption). The rest of the app uses node-redis (the official Redis Node.js client). Both connect to the same Redis instance via REDIS_URL. This is a documented BullMQ requirement, not a design choice.

Q74 What happens when the ZSET rate limiter key expires?

Redis automatically deletes the key when its TTL expires — this is cleanup. The TTL is set to Math.ceil(windowMs / 1000) on every request. If a user is inactive for longer than the window, the key disappears, and the next request starts fresh with count = 1. No manual garbage collection needed.

Q75 How does setEx() work and where is it used?

setEx(key, ttlSeconds, value) atomically sets a value AND its expiry in one command. Used in: cache (cacheSet) and idempotency store. It's preferred over separate set() + expire() because it's atomic — there's no window where the key exists without a TTL.

Q76 Explain the isOpen check before Redis operations.

Every Redis operation first checks redisClient.isOpen. If false (Redis is disconnected/unavailable), the function returns a fallback (null for reads, no-op for writes). This is the fail-open pattern. It prevents the app from throwing unhandled errors when Redis is temporarily down and keeps the request processing pipeline moving.

Q77 How is cache invalidation done and what's the "two-key" delete?

On any problem write (create/update/delete), invalidateProblemCache(id) calls cacheDel("problems:all", "problem:{id}") — it deletes BOTH the list cache and the individual problem cache in one call. cacheDel accepts variadic keys and passes them as an array to redisClient.del(keys). This ensures both caches are always consistent with the DB.

Q78 What is a Redis pipeline vs a transaction? Which does the rate limiter use?

A pipeline batches commands in one network round-trip but doesn't guarantee atomicity. A transaction (MULTI/EXEC) batches commands AND guarantees they execute atomically — no other commands interleave. The rate limiter uses multi() which is a transaction. This matters because another request from the same user could race between ZREMRANGEBYSCORE and ZCARD, giving an incorrect count.

Q79 How does the sendCommand() call work for leaderboard ZADD?

For the "LT" flag (ZADD only updates if the new score is less than the current one), node-redis's typed API doesn't directly support it. So the code uses redisClient.sendCommand(["ZADD", key, "LT", score, member]) — this sends a raw Redis command. It's used for recordBestRuntime to keep only the fastest (lowest) runtime per user per problem.

Q80 What data structure would you use if you needed a time-series of submissions?

Redis Streams (XADD/XREAD) for real-time append-only log with time-based IDs, or TimeSeries module for aggregated metrics. For the activity calendar (submissions per day), MongoDB aggregation with $dateToString is already used — this is fine since it's a batch query for profile stats, not a hot real-time path.

Q81 How would you handle Redis failover in production?

Use Redis Sentinel (automatic failover) or a managed service like Redis Cloud / ElastiCache with multi-AZ replicas. The node-redis client supports Sentinel configuration. The fail-open design means brief outages don't crash the app — the system degrades gracefully to no caching, no rate limiting (temporarily), and uses JWT expiry as the only logout mechanism.

Q82 What's the memory impact of storing full JWTs as blocklist keys?

JWTs are ~200-300 bytes. With 1-hour expiry, at most you'd have active_users * sessions_per_user keys at once. For thousands of users, this is a few MB — negligible for Redis. The expireAt ensures automatic cleanup. At massive scale, you could hash the JWT (SHA-256 = 32 bytes) instead of storing the full token.

Queue

📦 BullMQ — Job Queue & Workers (Q83–Q105)

Q83 What is BullMQ and why use it over RabbitMQ or Kafka?

BullMQ is a Node.js job queue library built on Redis. Chosen because: (1) We already have Redis — no additional infrastructure. (2) It's Node-native with excellent TypeScript/Promise support. (3) Perfect for task queues (not streaming). RabbitMQ would add a separate broker to manage. Kafka is for high-throughput event streaming — overkill for ~10 submissions/minute. BullMQ is the right tool for this scale.

Q84 Explain the Producer-Consumer pattern as implemented.

Producer (submissionQueue.js): Creates a BullMQ Queue, exports enqueueSubmission() which calls queue.add("evaluate", payload, { jobId: submissionId }). The controller calls this and returns 202.
Consumer (submissionWorker.js): Creates a BullMQ Worker with a processor function that calls processSubmission(). It runs with concurrency: 5.
Communication: They share the same Redis and queue name ("submissions") but can be in different processes.

Q85 What does concurrency: 5 mean and why that number?

The worker processes at most 5 jobs simultaneously. This is back-pressure control. Judge0's RapidAPI plan has rate limits (~100 requests/minute). Each submission may make 2 API calls (submit batch + poll). With concurrency 5, at most 10 Judge0 calls run in parallel. The rest queue up and wait their turn. This prevents quota exhaustion during traffic spikes.

Q86 What happens when a job fails? Describe the retry policy.

Configured in defaultJobOptions: attempts: 3 with backoff: { type: "exponential", delay: 2000 }. So: 1st retry after 2s, 2nd after 4s, 3rd after 8s. If all 3 fail, the job is marked as permanently failed. removeOnFail: false keeps failed jobs in Redis for inspection (acting as a dead-letter queue). removeOnComplete: 1000 keeps the last 1000 completed jobs for debugging.

Q87 What is UnrecoverableError and when is it thrown?

BullMQ's UnrecoverableError bypasses the retry policy — the job is immediately marked as failed, no retries attempted. The worker throws it when the circuit breaker is open: if (/breaker is open/i.test(err.message)) throw new UnrecoverableError(err.message). Rationale: if Judge0 is down (breaker open), retrying after 2/4/8 seconds won't help — the breaker stays open for 30 seconds. Fail fast so the user gets feedback immediately.

Q88 Why is jobId: submissionId set when enqueuing?

BullMQ uses jobId for deduplication. If a job with the same ID already exists in the queue, adding it again is a no-op. This prevents the same submission from being evaluated twice if the enqueue call is somehow retried (e.g., network glitch). Combined with the Idempotency-Key middleware, this provides two layers of duplicate protection.

Q89 How does the worker return results to the web tier?

The worker's processor function returns the result object (containing submissionId, userId, accepted, status, etc.). BullMQ stores this as the job's returnvalue. BullMQ's QueueEvents class (in socket.js) listens for completed events, extracts returnvalue, and emits it via Socket.io to the user's room. This is a Pub/Sub bridge: BullMQ → Socket.io → browser.

Q90 What's the QueueEvents class and how does it differ from the Worker?

Worker processes jobs (pulls from queue, executes handler). QueueEvents is a passive listener — it subscribes to Redis keyspace notifications to receive events (completed, failed, progress) about jobs without processing them. In socket.js, QueueEvents listens for completed/failed events and bridges them to Socket.io. The Worker and QueueEvents can be in different processes.

Q91 How does the failed-job notification work in socket.js?

QueueEvents listens for the failed event. When a job exhausts retries, socket.js fetches the job data (submissionQueue.getJob(jobId)) to get the userId, then emits a submission:result event with an error status. It even checks if the failure was due to a breaker-open error and provides a user-friendly message. This prevents the UI from hanging forever on "judging...".

Q92 What is exponential backoff and why use it for retries?

Exponential backoff increases the delay between retries: 2s → 4s → 8s. This prevents thundering herd: if Judge0 goes down and 100 jobs fail simultaneously, they don't all retry at the same instant. The staggered retries give the external service time to recover without being overwhelmed by a burst of retries.

Q93 Can the worker run in a separate process? How?

Yes — npm run worker runs src/workers/index.js, which connects to the same MongoDB and Redis, then calls createSubmissionWorker(). Since BullMQ coordinates through Redis, the worker process doesn't need any direct communication with the web process. You can run multiple worker instances for horizontal scaling. On Render, this would be a separate type: worker service (paid).

Q94 What are the tradeoffs of in-process vs separate worker?

In-process: Simple, one deployment, free on Render. But: worker and web server share CPU/memory; a long-running evaluation blocks event loop for web requests; can't scale independently. Separate process: Independent scaling, isolated resources, better fault isolation. But: additional cost, deployment complexity. The RUN_WORKER_IN_PROCESS flag makes this a runtime config decision.

Q95 What is removeOnComplete: 1000?

After a job completes successfully, BullMQ keeps it in Redis for inspection. removeOnComplete: 1000 means: keep the last 1000 completed jobs and auto-delete older ones. This provides a debugging window (you can inspect recent jobs via BullMQ's dashboard) while preventing unbounded Redis memory growth.

Q96 What is removeOnFail: false?

Failed jobs are never automatically deleted. They remain in Redis indefinitely, acting as a dead-letter queue. You can inspect them to understand why they failed, retry them manually, or build alerting on failure counts. In production, you'd add a cleanup cron for jobs older than N days.

Q97 How does BullMQ handle process crashes mid-job?

BullMQ uses a lock mechanism. When a worker picks a job, it acquires a lock (a Redis key with a TTL). If the worker crashes, the lock expires, and BullMQ considers the job as failed/stalled. It can then be retried by another worker. This provides at-least-once delivery — a job might be processed more than once on failure, but never lost.

Q98 What Redis data structures does BullMQ use internally?

BullMQ uses: Lists (LPUSH/BRPOPLPUSH for the queue), Hashes (job data and metadata), Sorted Sets (delayed/prioritized jobs, scheduled retries), Strings (locks, counters), and Pub/Sub channels (QueueEvents notifications). A single queue creates ~6 Redis keys with the prefix bull:{queueName}:.

Q99 How would you monitor the queue in production?

Options: (1) Bull Board or Arena — web dashboards that connect to the same Redis and display queue stats, job statuses, and allow manual retries. (2) Custom metrics: expose queue.getJobCounts() (waiting, active, completed, failed) via a /metrics endpoint, scraped by Prometheus. (3) Alerting on failed count exceeding a threshold.

Q100 What's the difference between add() and addBulk() in BullMQ?

add() enqueues a single job. addBulk() enqueues multiple jobs in one Redis round-trip — useful for batch operations. The project uses add() since each submission is enqueued individually as it arrives. Batch enqueue would be useful if, say, an admin re-evaluates all submissions for a problem.

Q101 How does BullMQ's maxRetriesPerRequest: null work?

ioredis normally retries failed Redis commands a limited number of times. BullMQ's blocking operations (like BRPOPLPUSH, which waits for new jobs) can block for a long time. If ioredis gives up retrying, the worker stops receiving jobs. maxRetriesPerRequest: null tells ioredis to retry forever — ensuring the worker reconnects after transient Redis outages.

Q102 What is "at-least-once" vs "at-most-once" vs "exactly-once" delivery?

At-most-once: Job processed 0 or 1 times (fire-and-forget). At-least-once: Job processed 1+ times (retries, but may duplicate). Exactly-once: Job processed exactly 1 time (hardest, requires dedup). BullMQ provides at-least-once. The jobId: submissionId deduplication and the idempotency middleware together approximate exactly-once behavior at the application level.

Q103 Why does enqueueSubmission set the job name to "evaluate"?

queue.add("evaluate", payload, options) — "evaluate" is the job name. In BullMQ, different named jobs can have different processor handlers (using worker.on('evaluate', handler)). Currently there's only one job type, but the architecture allows adding more (e.g., "re-evaluate", "batch-check") without changing the queue. It's future-proofing.

Q104 How would you add job priority to the submission queue?

BullMQ supports priority via queue.add(name, data, { priority: 1 }) — lower number = higher priority. You could give premium users priority 1 and free users priority 5. BullMQ uses a Redis ZSET scored by priority to manage the order. Jobs with the same priority are FIFO.

Q105 What happens to queued jobs if the backend restarts?

Jobs are stored in Redis, not in the Node.js process. When the backend restarts, the worker reconnects to Redis and resumes processing pending jobs. Any jobs that were mid-execution when the crash happened will be retried after their lock expires (stalled job recovery). No jobs are lost — this is a key advantage of a persistent queue.

Resilience

🔌 Circuit Breaker & Judge0 (Q106–Q122)

Q106 What is the Circuit Breaker pattern and why is it needed?

Without a circuit breaker, if Judge0 goes down, every submission would wait 20 seconds (timeout), consuming worker threads and degrading the entire system. The circuit breaker monitors failure rates. When failures exceed a threshold, it opens (trips) and immediately rejects all subsequent calls for a cooldown period — failing fast (~1ms) instead of waiting for timeouts. After the cooldown, it enters half-open state, letting one probe request through to test recovery.

Q107 Explain the three states of the circuit breaker.

CLOSED (normal): All requests pass through. Failures are counted. OPEN (tripped): All requests are immediately rejected with "Breaker is open" error. Timer runs for resetTimeout (30s). HALF-OPEN (probing): One request is allowed through. If it succeeds → CLOSED. If it fails → OPEN again. The opossum library logs state transitions: "Judge0 circuit OPEN — failing fast", "HALF-OPEN — probing", "CLOSED — recovered".

Q108 What are the opossum configuration parameters and what do they mean?

timeout: 20000 — a batch must resolve within 20s or it's counted as a failure. errorThresholdPercentage: 50 — open the breaker once 50% of recent calls fail. resetTimeout: 30000 — stay open for 30s before trying half-open. volumeThreshold: 5 — need ≥5 calls in the measurement window before the breaker can trip (prevents premature tripping on 1 out of 2 calls = 50%).

Q109 What is the Adapter Pattern in judge0Adapter.js?

The adapter provides a clean, stable interface: judge0Adapter.execute(submissions) and judge0Adapter.getLanguageId(language). Controllers and services depend on this interface, not on the raw Judge0 HTTP details (URLs, headers, polling logic). To switch from Judge0 RapidAPI to a self-hosted judge, you'd only change the adapter — no other file needs modification. This is the Dependency Inversion Principle in action.

Q110 How does the batch submission to Judge0 work?

Step 1: POST to /submissions/batch with an array of {source_code, language_id, stdin, expected_output}. Judge0 returns an array of tokens (UUIDs). Step 2: GET /submissions/batch?tokens=t1,t2,t3&fields=* to poll results. Keep polling every 1 second until all status_id > 2 (1=In Queue, 2=Processing, 3=Accepted, 4+=terminal states). Max 30 attempts. Step 3: Return the submissions array with status, time, memory, stderr, etc.

Q111 What's the Template Method pattern in evaluateTestcases()?

evaluateTestcases(code, language, testcases) is the shared evaluation skeleton. Both runCode (visible tests, synchronous) and the submission worker (hidden tests, async) call the same function — they only differ in: (1) which test case array is passed, and (2) what they do with the result (run returns it directly; worker saves to DB + updates leaderboard). The invariant algorithm (build batch → execute → parse) is defined once.

Q112 What was Bug 1 (the setTimeout bug) and how was it fixed?

The old waiting() function had setTimeout(() => { return; }, timer) — the return was inside setTimeout's callback, not the outer function. The promise resolved immediately (with undefined) instead of waiting. Fix: const waiting = (timer) => new Promise(resolve => setTimeout(resolve, timer)) — properly wraps setTimeout in a Promise that resolves after the delay.

Q113 What was Bug 3 (the infinite polling loop)?

The original submitToken() polled Judge0 results in an infinite while(true) loop with no exit condition. If Judge0 never returned results (stuck token), it would loop forever, consuming CPU and never resolving. Fix: Added MAX_ATTEMPTS = 30 with a for loop, and throws an error after 30 seconds: "Judge0 timed out: results not ready after 30s".

Q114 How does the circuit breaker interact with BullMQ retries?

When the breaker is open, it throws immediately. The worker catches this and wraps it in UnrecoverableError, which tells BullMQ to skip all retries and fail immediately. Without this, BullMQ would retry 3 times with backoff (2s, 4s, 8s = 14s total), during which the breaker is still open (30s). Using UnrecoverableError gives the user feedback in <1 second instead of after 14 seconds.

Q115 What's the volumeThreshold: 5 setting for?

Prevents the breaker from tripping prematurely. If only 2 requests were made and 1 failed, that's 50% failure rate — but it might just be a transient error. volumeThreshold: 5 requires at least 5 requests in the measurement window before the percentage check applies. This avoids false positives during low-traffic periods.

Q116 How does the "Run" endpoint handle a breaker-open error?

In runCode, the catch block checks /breaker is open/i.test(err.message). If true, it returns 503 Service Unavailable with a user-friendly message: "Judge is temporarily unavailable. Please try again in a moment." If it's any other error, it returns 500. The 503 status code is semantically correct for temporary unavailability.

Q117 What language IDs does Judge0 use and how are they mapped?

getLanguageById() maps: "c++"→54, "java"→62, "javascript"→63. These are Judge0 CE (Community Edition) language IDs. The controller normalizes "cpp" to "c++" before passing to the adapter. If a new language is added, only this mapping and the schema enum need updating.

Q118 What is status_id in Judge0 results?

Judge0 status IDs: 1=In Queue, 2=Processing, 3=Accepted, 4=Wrong Answer, 5=Time Limit Exceeded, 6=Compilation Error, 7-14=various runtime errors. The polling loop waits until all status_id > 2. The evaluator maps: 3→"accepted", 4→"wrong", anything else→"error".

Q119 Why does breaker.fire() not use breaker.call()?

fire() and call() are effectively the same in opossum — fire() is the preferred API. It passes the arguments to the wrapped function (executeRaw), respects the circuit state, and returns a Promise. If the breaker is open, it immediately rejects without calling the function.

Q120 How would you add fallback behavior to the circuit breaker?

Opossum supports breaker.fallback(fn) — a function called when the breaker is open. You could return a "service unavailable" response, or queue the request for later retry, or use a cached previous result. Currently, the project lets the error propagate to the caller (worker or controller) which handles it appropriately.

Q121 What metrics does opossum track internally?

Opossum tracks: success count, failure count, timeout count, rejection count (breaker open), latency percentiles, and event history. You can access these via breaker.stats or listen to events: breaker.on('success'), breaker.on('failure'), breaker.on('timeout'), breaker.on('reject'). These can be exported to Prometheus for monitoring.

Q122 What's the Saga / Compensating Transaction in submissionService.js?

The processSubmission function has a try/catch saga: Try: evaluate → save verdict → update user + leaderboard. Catch (compensating action): If ANY step fails, set submission.status = "error" and submission.errorMessage = "Evaluation failed: " + err.message, then rethrow for BullMQ retry. This ensures a submission never stays stuck on "pending" — it either succeeds or moves to an explicit error state.

Real-Time

🔌 WebSocket & Socket.io (Q123–Q138)

Q123 Why Socket.io instead of raw WebSockets or SSE?

Socket.io provides: (1) Automatic fallback to long-polling if WebSocket isn't available. (2) Rooms — users join a room named after their userId; we emit to that room. (3) Reconnection — auto-reconnect with backoff on disconnection. (4) CORS handling built-in. (5) Structured events (named channels like "submission:result"). Raw WebSockets would require building all of this from scratch. SSE (Server-Sent Events) is one-directional (server→client only) — Socket.io supports bidirectional communication.

Q124 How does the room-based push work?

When a user connects, the client emits socket.emit("join", userId). The server handles this: socket.join(userId.toString()). When a submission completes, the server does io.to(result.userId).emit("submission:result", result) — this sends the verdict only to sockets in that user's room. Other users don't receive it. If the user has multiple tabs open, all tabs receive the event (they're all in the same room).

Q125 How does the QueueEvents → Socket.io bridge work?

In socket.js, after creating the Socket.io server, a BullMQ QueueEvents instance subscribes to the "submissions" queue. On the completed event, it receives { returnvalue } — the JSON result from the worker. It parses the result, extracts userId, and emits via Socket.io. This bridges two different Pub/Sub systems: BullMQ (Redis-based) → Socket.io (WebSocket-based).

Q126 What happens if the user's browser disconnects before the verdict arrives?

The Socket.io emit goes to an empty room — the event is silently discarded. But the submission result is also persisted to MongoDB. The user can: (1) Reconnect and poll GET /submission/status/:submissionId. (2) View it in their submission history on the problem page. The WebSocket push is the fast path; the database is the reliable fallback.

Q127 Why is there no auth on the Socket.io connection?

The current implementation trusts the client-sent userId on the join event. This is a simplification. In production, you'd verify the JWT cookie in the Socket.io io.use() middleware: extract the cookie, verify the JWT, and use the decoded _id as the room name. The current approach works because the socket is only used for receiving (not sending sensitive data).

Q128 How does the frontend Socket.io client work?

utils/socket.js creates a single shared socket: io(VITE_API_URL, { withCredentials: true, autoConnect: true }). withCredentials sends cookies (for potential future auth). autoConnect: true connects immediately on import. The ProblemPage component emits socket.emit("join", userId) and listens for socket.on("submission:result", callback) to update the UI when a verdict arrives.

Q129 Why is the socket instance a module-level singleton?

Creating multiple socket connections to the same server would waste resources and cause duplicate events. By exporting a single socket instance from utils/socket.js, all React components share the same connection. This is the Singleton pattern applied to a network resource.

Q130 How would you scale Socket.io across multiple server instances?

Use the Socket.io Redis adapter (@socket.io/redis-adapter). It uses Redis Pub/Sub so that an io.to(userId).emit() on Server A is forwarded to Server B (which might hold the user's actual WebSocket connection). Without the adapter, Socket.io only emits to connections on the local process. BullMQ QueueEvents already uses Redis, so both processes see the event — the gap is Socket.io rooms, which are process-local by default.

Q131 What's the difference between io.emit(), io.to().emit(), and socket.emit()?

io.emit(event, data) — broadcast to ALL connected clients. io.to(room).emit(event, data) — send to all sockets in a specific room. socket.emit(event, data) — send to that ONE specific socket only. The project uses io.to(userId).emit() to target a specific user's room. Never uses broadcast (that would leak verdicts to everyone).

Q132 Why is typeof result === "string" checked in the QueueEvents handler?

BullMQ's returnvalue might be serialized as a JSON string depending on the Redis client version or BullMQ version. The code defensively checks: if it's a string, JSON.parse() it; if it's already an object, use it directly. This prevents crashes from unexpected serialization behavior.

Q133 How does Socket.io handle reconnection?

Socket.io client has built-in reconnection with exponential backoff. If the connection drops (server restart, network issue), it automatically attempts to reconnect. On reconnection, the client should re-emit join to re-enter the room. The autoConnect: true option means the connection is established immediately when the module is imported.

Q134 What transport does Socket.io use?

Socket.io initially connects via HTTP long-polling (for reliability), then upgrades to WebSocket if the environment supports it. This is the "transport upgrade" mechanism. On Render's web service, WebSocket is supported, so the upgrade happens. On Vercel serverless, WebSocket is NOT supported — which is why the Vercel entry point (server.js) doesn't initialize Socket.io.

Q135 Why does initSocket() return io and export getIO()?

initSocket(server) creates the Socket.io instance and returns it. getIO() provides access to the same instance from other modules (if needed). This avoids circular dependencies and ensures the socket is initialized only once (with the HTTP server). It's a lazy singleton accessor pattern.

Q136 What happens to pending events when the user is offline?

They're lost — Socket.io doesn't queue events for offline clients. When the user reconnects, they won't receive events emitted during their disconnection. This is acceptable because the database is the source of truth. The user can poll /submission/status/:id or see the result in their submission history. The WebSocket push is an optimization, not the only delivery mechanism.

Q137 Could you replace Socket.io push with polling? What are the tradeoffs?

Yes — the GET /submission/status/:submissionId endpoint exists as a polling fallback. Tradeoffs: Polling is simpler (no WebSocket infrastructure) but adds latency (poll interval), wastes bandwidth (empty responses), and doesn't scale well (N users × M polls/sec). Push is instant (zero-latency) and efficient (only sends when there's data) but requires WebSocket infrastructure and doesn't work on serverless (Vercel).

Q138 How does the CORS config for Socket.io relate to the Express CORS config?

Both use the same allowedOrigins array from origins.config.js. Express CORS is handled by the cors middleware. Socket.io CORS is configured in the Server constructor: cors: { origin: allowedOrigins, credentials: true }. They must match — otherwise the browser would block the WebSocket upgrade handshake (which starts as an HTTP request subject to CORS).

Leaderboard

🏆 Leaderboard — Redis Sorted Sets (Q139–Q152)

Q139 Why use Redis Sorted Sets (ZSET) instead of a MongoDB query for leaderboards?

A MongoDB approach would require: User.find().sort({score: -1}).limit(50) — this is O(N log N) on every request (sorting all users). A Redis ZSET maintains elements in sorted order by score. ZREVRANGE retrieves the top-50 in O(log N + 50) — essentially constant time regardless of user count. At 100K users, MongoDB sort takes hundreds of milliseconds; Redis ZSET takes <1ms. It's the right data structure for ranked access.

Q140 How are the two types of leaderboard structured?

Global leaderboard (leaderboard:global): member = userId, score = weighted solve count (easy=1, medium=3, hard=5 points). Uses ZINCRBY to add points on each first solve. Per-problem leaderboard (leaderboard:problem:{id}): member = userId, score = best runtime in milliseconds. Uses ZADD LT (Less Than flag) — only updates if the new score is lower than the existing one, keeping the fastest time.

Q141 What is ZADD LT and why is it critical?

ZADD key LT score member only updates the score if the new score is less than the current one. This ensures we always keep the fastest (lowest) runtime per user per problem. Without LT, a slower subsequent submission would overwrite the best time. This is an atomic, idempotent operation — safe for concurrent submissions.

Q142 Why ZREVRANGE for global but ZRANGE for per-problem?

Global leaderboard: higher score = more problems solved = better. ZREVRANGE returns members in descending score order (highest first). Per-problem leaderboard: lower score = faster runtime = better. ZRANGE returns members in ascending score order (lowest first). The sort direction matches the ranking semantics.

Q143 How does the weighting system work?

WEIGHT = { easy: 1, medium: 3, hard: 5 }. On first accept, ZINCRBY leaderboard:global WEIGHT[difficulty] userId. So solving 10 easy problems (10 pts) ranks below solving 2 hard problems (10 pts) if someone also solved 1 easy (11 pts). The weighting incentivizes tackling harder problems.

Q144 How is double-counting prevented on the leaderboard?

In submissionService.js, before calling leaderboard.addSolve(), the code checks: user.problemSolved.some(p => p.toString() === problemId.toString()). If the user has already solved this problem, addSolve() is NOT called. Points are only added on the first accepted submission per problem. The $addToSet on problemSolved is also idempotent.

Q145 How is the user's percentile calculated?

percentile = Math.round(((total - rank) / total) * 100) where rank is 0-based (from ZREVRANK) and total is from ZCARD. If you're rank 5 out of 100, percentile = (100-5)/100 * 100 = 95%. This means you're in the top 5%. If not ranked (no solves), percentile is null.

Q146 What does ZREVRANK return?

The 0-based rank of a member in descending order. Rank 0 = highest score = #1 on the leaderboard. The controller adds 1 for display: rank1 = rank + 1. If the member doesn't exist in the ZSET, ZREVRANK returns null.

Q147 Why does parseFlat() exist?

Redis ZRANGE/ZREVRANGE ... WITHSCORES returns a flat array: [member1, score1, member2, score2, ...]. parseFlat() converts this to [{userId, score}, ...] by iterating in steps of 2. It's a utility to transform Redis's wire format into a usable JavaScript structure.

Q148 How does attachNames() resolve userIds to names?

The leaderboard ZSET only stores userIds (strings). attachNames() extracts all IDs, does a single User.find({ _id: { $in: ids } }).select("firstName") — ONE database query for all users. It builds a Map for O(1) lookup, then maps entries to include firstName. This is the N+1 query optimization: 1 query instead of 50.

Q149 What does the safe() wrapper function do?

safe(fn, fallback) wraps every Redis call: if Redis is closed or the call throws, return the fallback (e.g., empty array, {rank:null, score:0, total:0}). This is the fail-open pattern applied to leaderboard operations. The leaderboard is a nice-to-have; it shouldn't take down the API.

Q150 Why convert runtime from seconds to milliseconds for the per-problem leaderboard?

Judge0 returns runtime in seconds (float, e.g., 0.042). Storing as milliseconds (integer, 42) avoids floating-point precision issues in Redis ZSET scores and gives cleaner display values. Math.round((runtimeSeconds || 0) * 1000) handles the conversion.

Q151 How would you implement a weekly/monthly leaderboard?

Use time-bucketed keys: leaderboard:global:2026-W30 (ISO week). On each solve, ZINCRBY both the permanent key and the current week/month key. Set a TTL on the time-bucketed key (e.g., 35 days for monthly) for automatic cleanup. The frontend would show tabs: All Time, This Week, This Month — each querying a different key.

Q152 What's the time complexity of each leaderboard operation?

ZINCRBY: O(log N). ZADD LT: O(log N). ZREVRANGE 0 49 WITHSCORES: O(log N + 50). ZREVRANK: O(log N). ZSCORE: O(1). ZCARD: O(1). All operations are sub-millisecond at any practical scale. This is why Redis ZSET is the right data structure for leaderboards.

Reliability

🔄 Idempotency & Saga (Q153–Q162)

Q153 What does "idempotent" mean and why does it matter for submissions?

An idempotent operation produces the same result no matter how many times it's executed. For submissions: a network glitch might cause the browser to retry the POST. Without idempotency, the same code would be submitted and judged twice, wasting Judge0 quota, creating duplicate records, and confusing the user. With the Idempotency-Key header, the second request gets the cached response from the first — no duplicate work.

Q154 Who generates the Idempotency-Key?

The client (frontend) generates a unique key per action — typically a UUID or a hash of (userId + problemId + timestamp). The key is sent as an HTTP header. The server doesn't generate it because the server can't distinguish a retry from a new request without client-provided context. This follows the same pattern as Stripe's idempotency keys.

Q155 What if the idempotency key is not sent?

The middleware checks if (!key) return next() — the request proceeds normally without idempotency protection. This is fail-open: not sending the header is valid (older clients, testing, etc.). The middleware is an enhancement, not a requirement.

Q156 Why is the idempotency TTL 24 hours?

It needs to be long enough to cover: network retries (seconds), user double-clicks (seconds), and a user potentially navigating away and coming back to retry (minutes to hours). 24 hours is generous enough to cover all retry scenarios. It also auto-cleans up — old keys don't accumulate forever.

Q157 Why only cache 2xx responses in the idempotency middleware?

If the first request failed (4xx/5xx), the client should be able to retry with the same key and get a fresh attempt. Caching error responses would prevent recovery — the client would keep getting the same error. Only successes are cached because they represent completed work that shouldn't be duplicated.

Q158 What is a Saga pattern?

In distributed systems, a saga is a sequence of local transactions where each step has a compensating action. If step 3 fails, you run the compensating actions for steps 2 and 1 to undo partial work. In submissionService.js, the saga is: evaluate → save verdict → update user/leaderboard. If any step fails, the compensating action sets status: "error" and errorMessage, ensuring the submission is never left in "pending" state.

Q159 What's the compensating action in submissionService.js?

In the catch block: submission.status = "error"; submission.errorMessage = "Evaluation failed: " + err.message; await submission.save().catch(() => {}). The .catch(() => {}) on save ensures that even if MongoDB is also failing, we don't throw a secondary error — we just silently fail the compensating write and rethrow the original error for BullMQ to handle.

Q160 How do idempotency and BullMQ's jobId dedup work together?

They provide two layers of protection: (1) HTTP level: the idempotency middleware prevents the controller from even executing on a retry — the cached response is replayed. (2) Queue level: BullMQ's jobId: submissionId prevents duplicate jobs. If the idempotency cache misses (expired, Redis restart) but the job was already queued, BullMQ silently ignores the duplicate add. Belt and suspenders.

Q161 What happens if step 2 (save verdict) fails but step 1 (evaluate) succeeded?

The compensating action marks the submission as "error". The user sees "Evaluation failed." The Judge0 work is wasted (can't un-execute code), but the database is in a consistent state. On BullMQ retry, processSubmission runs again — it finds the submission (still "pending" status because the save in step 2 failed), re-evaluates, and tries again. The 3-attempt retry policy gives it multiple chances.

Q162 How does $addToSet help with idempotent leaderboard updates?

If the leaderboard update crashes and BullMQ retries, $addToSet: { problemSolved: problemId } won't add a duplicate. And the alreadySolved check prevents calling leaderboard.addSolve() again. Even if both safeguards fail, ZINCRBY on a ZSET is NOT idempotent (it would double-add points). This is why the alreadySolved check is the critical gate — it prevents double-counting at the application level.

The async function does the API call. On success, it returns data (→ action.payload in fulfilled). On error, it calls rejectWithValue(message) (→ action.payload in rejected). This eliminates manual action types and dispatch boilerplate.

Q185 Why withCredentials: true on both Axios and Socket.io?

Q187 How does the GitHub Actions cron workflow work?

keep-alive.yml runs on two cron schedules: every 10 minutes from 03:00-16:00 UTC (08:30-21:30 IST) and at 16:00 UTC (21:30 IST). It curls the API_HEALTH_URL with retries (5 attempts, 60s timeout each, 15s between retries). This keeps the Render free-tier service alive during Indian business hours and wakes it after overnight sleep. The URL is stored as a repository variable (not a secret — it's public).

Q188 Why IST time windows for keep-alive?

The platform targets Indian users. Active hours are 08:30-21:30 IST. Outside this window, the service sleeps to conserve Render's free-tier instance hours (750 hours/month). The in-app self-ping and GitHub cron both skip pings outside this window. This pragmatic optimization makes the free tier work for a side project.

Q189 What's the difference between the self-ping and the GitHub cron ping?

The self-ping (in index.js) keeps the service from sleeping when it's already running — it pings /health every 14 minutes. But if the service is already asleep, the self-ping code isn't running! The GitHub cron runs on GitHub's infrastructure (external to Render), so it can wake a sleeping service by hitting it from outside. The first request takes ~50 seconds (cold start), hence the retry logic.

Q190 What is Render Blueprint (Infrastructure as Code)?

render.yaml defines services declaratively: type (web), runtime (node), build/start commands, health check path, environment variable groups with sync: false for secrets. When you connect the repo to Render via "New → Blueprint", Render reads this file and creates everything automatically. Changes to the YAML trigger service updates on the next deploy. It's similar to Terraform or AWS CloudFormation but specific to Render.

Q191 Why is the Render region set to Singapore?

Singapore is the closest Render region to India — lower latency for Indian users. MongoDB Atlas cluster should also be in the same region (Mumbai or Singapore) to minimize database query latency. Co-locating compute and data in the same region is a fundamental latency optimization.

Q192 How does autoDeploy: true work?

Every push to the main branch triggers an automatic build and deploy on Render. Render watches the GitHub repo via a webhook. On push: install dependencies (npm install), start the service (npm start), wait for the health check to pass, then swap traffic to the new instance. If the health check fails, the deploy is rolled back.

Q193 What are the environment variables and how are secrets managed?

Secrets (DB_CONNECT_STRING, REDIS_URL, JWT_KEY, JUDGE0_KEY, API keys) are stored in Render's dashboard with sync: false — never committed to the repo. Non-secrets (OPENROUTER_MODEL, RUN_WORKER_IN_PROCESS) are set in the YAML directly. .env files are in .gitignore for local development only.

Q194 How does Vercel host the frontend?

Vercel detects the Vite project, runs npm run build (which produces a dist/ folder of static HTML/JS/CSS), and serves it from a global CDN. The vercel.json rewrite ensures all paths serve index.html for client-side routing. VITE_API_URL is set in Vercel's environment variables dashboard to point to the Render backend.

Q195 How would you add CI/CD with testing?

Add a GitHub Actions workflow: on PR/push → install deps → run linter (npm run lint) → run unit tests (Jest for backend, Vitest for frontend) → run integration tests (Supertest for API endpoints with a test MongoDB). Only if all pass → merge allowed. Vercel and Render already do CD (auto-deploy on push). The missing piece is CI (automated testing).

Q196 What does .unref() do on the keep-alive timer?

setInterval(...).unref() tells Node.js: don't keep the event loop alive just for this timer. If all other work is done and the server shuts down, the unreffed timer won't prevent process exit. Without it, a graceful shutdown would hang waiting for the next interval tick. It's a Node.js process lifecycle best practice.

Q197 How do you monitor the production backend?

Currently: Render's built-in logs and metrics (CPU, memory, request count). The /health endpoint provides basic liveness. To improve: add structured JSON logging (winston/pino), expose /metrics for Prometheus, add Sentry for error tracking, add Bull Board for queue monitoring, and set up PagerDuty/Slack alerts on health check failures or error rate spikes.

Security

🛡️ Security & Best Practices (Q198–Q210)

Q198 How is XSS (Cross-Site Scripting) prevented?

httpOnly cookies prevent JavaScript from accessing the JWT. React auto-escapes JSX output (no dangerouslySetInnerHTML except where explicitly needed). Discussion text is trimmed and length-limited (2000 chars). The AI chat uses markdown rendering, which should sanitize HTML. To further harden: add Content-Security-Policy headers and sanitize user-generated HTML with DOMPurify.

Q199 How is CSRF (Cross-Site Request Forgery) mitigated?

sameSite: "none" with secure: true allows cross-origin cookies but only over HTTPS. The real CSRF protection comes from: (1) CORS restricting which origins can make requests (only whitelisted domains). (2) Custom Content-Type: application/json header — browsers don't send JSON POST from forms (form submissions use application/x-www-form-urlencoded). (3) For additional security, add CSRF tokens on state-changing routes.

Q200 How are passwords stored?

Passwords are hashed with bcrypt (salt rounds: 10) before storing in MongoDB. The original password is never stored or logged. On login, bcrypt.compare() hashes the attempt and compares — no plain-text comparison. Even if the database is compromised, passwords can't be easily reversed (bcrypt is intentionally slow to hash).

Q201 What's the NoSQL injection risk and how is it handled?

MongoDB is vulnerable to operator injection: { "password": { "$gt": "" } } would match any non-empty password. Mongoose schemas with typed fields (String, Number) reject object values — they're cast and validated. The emailId field has trim and lowercase transforms. However, for extra safety, you could add express-mongo-sanitize middleware to strip $ operators from request bodies.

Q202 How does Cloudinary signed upload prevent unauthorized uploads?

The backend generates a signature using the Cloudinary API secret: cloudinary.utils.api_sign_request(params, API_SECRET). The frontend uploads to Cloudinary with this signature. Cloudinary verifies the signature matches the parameters. Without the server-generated signature, you can't upload — the API secret is never exposed to the client. This is the signed upload security model.

Q203 What security headers should be added?

Use helmet middleware for: X-Content-Type-Options: nosniff (prevents MIME sniffing), X-Frame-Options: DENY (prevents clickjacking), Strict-Transport-Security (enforces HTTPS), Content-Security-Policy (restricts resource loading), X-XSS-Protection. These are not currently implemented — they'd be a good production hardening step.

Q204 Can a user see another user's code or hidden test cases?

Hidden test cases are never included in the getProblemById response — it uses .select() to exclude hiddenTestCases. Submissions belong to a userId; the status endpoint checks userId: req.result._id. However, the /submission/all endpoint returns all submissions (including code) without auth — this is a deliberate design choice for the public status page, but could be restricted.

Q205 What happens with code injection via submitted code?

User code runs in Judge0's sandboxed environment — not on the backend server. Judge0 uses Linux containers with resource limits (CPU time, memory, process count). Even malicious code (fork bombs, file system access) is contained. The backend never executes user code — it only forwards it to Judge0 via API. The separation of execution from the application server is a critical security boundary.

Q206 How is the JWT secret managed?

JWT_KEY is an environment variable — never hardcoded or committed. In render.yaml, it's marked sync: false (entered in dashboard). Locally, it's in .env which is in .gitignore. If the secret is compromised, all existing JWTs can be forged. You'd rotate the secret immediately, which invalidates all sessions (users must re-login).

Q207 What input validation exists beyond Mongoose schemas?

Backend: validator.js checks mandatory fields and email format. Mongoose enum validators for difficulty, language, role, status. maxLength: 2000 on discussion text. Frontend: Zod schemas for form validation (email format, password length). However, there's no explicit rate limiting on AI chat or video upload — these should be added.

Q208 What's the attack surface for the rate limiter?

IP-based limits can be bypassed with rotating proxies/VPNs. User-based limits require auth (harder to spam but you can create accounts). If Redis is down, the rate limiter fails open — all requests pass. Mitigation: add WAF (Cloudflare), combine IP + user limits, add CAPTCHA on auth routes, and consider fingerprinting.

Q209 How does the discussion delete check authorization?

deleteDiscussion checks: isAuthor = comment.userId.toString() === req.result._id.toString() AND isAdmin = req.result.role === "admin". If neither, returns 403. It also deletes all replies: Discussion.deleteMany({ $or: [{ _id: commentId }, { parentId: commentId }] }). This cascading delete prevents orphaned replies.

System Design

🌐 System Design & Scalability (Q211–Q230)

Q211 How would you scale ByteCode to 100K concurrent users?

Frontend: Already on Vercel CDN — scales automatically. API tier: Horizontal scaling behind a load balancer (multiple Express instances). Add Redis adapter for Socket.io. Workers: Scale separately from the API (that's why the in-process vs separate toggle exists). Add more workers with higher concurrency. Database: MongoDB Atlas auto-scales; add read replicas for read-heavy queries. Redis: Redis Cluster for sharding across multiple nodes. Judge0: Self-host instead of RapidAPI — run judge containers on Kubernetes for unlimited throughput.

Q212 What's the bottleneck in the current architecture?

Judge0 RapidAPI — external, rate-limited, adds latency. It's the single biggest bottleneck. Solutions: self-host Judge0, use judge containers directly, or implement a local evaluation engine. Secondary bottleneck: single Render web service (CPU/memory shared with worker). Solution: separate worker process, horizontal scaling.

Q213 Why is horizontal scaling possible with this architecture?

The API is stateless: auth state is in JWT (cookie), session state is in Redis, data is in MongoDB. Any API instance can serve any request. Workers coordinate through Redis (BullMQ). Socket.io rooms can be shared via Redis adapter. No instance holds critical in-memory state. This is why "shared-nothing" architecture enables horizontal scaling.

Q214 What is back-pressure and how does the system implement it?

Back-pressure prevents a fast producer from overwhelming a slow consumer. Here: users submit fast (producer), but Judge0 evaluation is slow (consumer). Worker concurrency: 5 limits simultaneous evaluations. If the queue grows, submissions wait — they don't overload Judge0. The 202 response tells the user their submission is queued, not lost. Rate limiting also provides back-pressure at the API level (10 submits/min/user).

Q215 Design a notification system for ByteCode (submission results, replies, etc.).

Create a Notification model: {userId, type, message, read, metadata, createdAt}. Producers: submission worker (verdict), discussion controller (reply/upvote). Delivery: real-time via Socket.io (push to user room), persisted in MongoDB for history. Consumer: frontend notification bell with unread count badge. API: GET /notifications (list), PATCH /notifications/:id/read, DELETE /notifications/:id.

Q216 How would you implement contest mode?

Create a Contest model: {title, startTime, endTime, problems[], participants[]}. Time-boxed access: problems visible only between start/end. Separate leaderboard ZSET per contest: leaderboard:contest:{id} scored by (problems_solved * 1000 - penalty_time). Lock submissions after end time. Real-time ranking updates via Socket.io. Add penalty for wrong submissions (like ICPC).

Q217 Compare REST vs GraphQL for this project. Why REST?

REST fits because: (1) API calls are well-defined (get problem, submit code, get leaderboard) — no need for flexible querying. (2) REST is simpler to implement and debug. (3) Cache-aside works naturally with REST (cache by URL). (4) GraphQL shines when clients need different views of the same data (mobile vs web) — not a concern here. (5) The team is more familiar with REST.

Q218 What's the CAP theorem and which tradeoffs does this system make?

CAP: you can have at most 2 of Consistency, Availability, Partition-tolerance. The system chooses AP (Availability + Partition tolerance): when Redis partitions, the system stays available (fail-open) at the cost of temporary inconsistency (e.g., rate limits not enforced, stale cache). MongoDB Atlas provides strong consistency within a region. This is the right tradeoff for a user-facing web app — downtime is worse than slightly stale data.

Q219 How would you implement a custom judge instead of Judge0?

Run Docker containers with language runtimes (GCC, JDK, Node). For each submission: (1) Start a sandboxed container with resource limits (cgroups: CPU time, memory, no network). (2) Mount the source code as a file. (3) Compile if needed. (4) Run with stdin from each test case. (5) Compare stdout to expected output. (6) Kill if time/memory exceeded. Use Kubernetes Jobs or AWS Fargate for scaling. The judge0Adapter.js would swap its HTTP calls for container orchestration calls.

Q220 What's the difference between vertical and horizontal scaling?

Vertical: Bigger machine (more CPU/RAM). Simple but has limits. Horizontal: More machines behind a load balancer. Requires stateless design. This architecture supports horizontal scaling because: JWT auth is stateless, Redis holds shared state, MongoDB is accessed by connection string. You can run 10 API instances and 5 worker instances — they all share the same Redis and MongoDB.

Q221 How would you add full-text search for problems?

Options: (1) MongoDB Atlas Search (built-in Lucene-based full-text search, simplest). (2) Elasticsearch (dedicated search engine, most powerful). (3) Redis Search (RedisSearch module). For this project, MongoDB Atlas Search is the best fit — no additional infrastructure, supports fuzzy matching, autocomplete, and relevance scoring on title/description/tags fields.

Q222 How does the system handle a thundering herd on cache invalidation?

When problems:all cache expires and 100 requests arrive, all miss the cache and query MongoDB — this is the "cache stampede." Mitigation strategies: (1) Lock-based: Only the first request queries DB; others wait for the cache to be populated. (2) Probabilistic early expiry: Refresh the cache before it expires. (3) Background refresh: A cron job keeps the cache warm. Currently, the 5-minute TTL and moderate traffic make this unlikely, but it's a valid scaling concern.

Q223 What is event-driven architecture and how does this project use it?

Events decouple producers from consumers. BullMQ is event-driven: the controller (producer) emits a "submission" event to the queue; the worker (consumer) processes it independently. QueueEvents is a pure event listener. Socket.io is event-driven: server emits events, client subscribes. The system could be further evolved with an event bus (e.g., EventEmitter, Redis Pub/Sub) for cross-cutting concerns like analytics, logging, or notifications.

Q224 How would you add rate limiting to protect against DDoS?

Layer defense: (1) CDN/WAF (Cloudflare) — blocks at the network edge before traffic hits the server. (2) Reverse proxy (nginx) — connection-level rate limiting. (3) Application — the existing Redis ZSET rate limiter for per-user/IP limits. (4) Queue — BullMQ concurrency limits Judge0 calls. A true DDoS should be handled at layers 1-2, not the application layer.

Q225 What are the tradeoffs of the AI chat implementation?

Pros: Problem-scoped context (can't go off-topic), Socratic teaching approach, streaming-ready architecture (OpenAI SDK). Cons: No rate limiting (users could spam expensive LLM calls), no conversation persistence (refreshing loses history), no streaming in current implementation (waits for full response). Improvements: add per-user rate limiting, persist chat history in MongoDB, implement SSE streaming for real-time token output.

Q226 Explain database indexing strategy for this project.

Explicit indexes: Submission: {userId:1, problemId:1} (compound index for user's submissions per problem). Implicit indexes from Mongoose unique: true: User.emailId, SolutionVideo.cloudinaryPublicId. Discussion.problemId has index: true. MongoDB auto-creates an _id index on every collection. Missing: index on Submission.status for the profile aggregation's $match: {status: 'accepted'} — adding it would speed up profile stats.

Q227 What observability would you add for production?

Logging: Structured JSON logs (pino/winston) with request IDs for tracing. Metrics: Prometheus + Grafana — API latency (p50/p95/p99), queue depth, Judge0 circuit breaker state, cache hit rate. Tracing: OpenTelemetry distributed traces across API → Queue → Worker → Judge0. Error tracking: Sentry for crash reports with stack traces and context. Alerting: PagerDuty/Slack on error rate spikes, queue depth > threshold, health check failures.

Q228 How would you handle database migrations with Mongoose?

Mongoose is schema-flexible (no strict migrations like SQL), but for production you'd use: (1) migrate-mongo — a migration tool that runs scripts in order. (2) For adding fields: use default values in the schema (existing documents get defaults on read). (3) For renaming/restructuring: write a migration script that bulk-updates documents. (4) For removing fields: $unset in a migration. Always test migrations against a staging database first.

Q229 What testing strategy would you implement?

Unit tests: Jest for services (mock DB/Redis), test evaluation logic, cache helpers, rate limiter logic. Integration tests: Supertest for API endpoints with a test MongoDB (mongodb-memory-server). Test auth flows, CRUD, submission pipeline. E2E tests: Cypress/Playwright for critical user flows (signup → solve → submit → see verdict). Load tests: k6 or Artillery to verify rate limits and back-pressure under concurrent submissions.

Q230 What would you change if you rebuilt this project from scratch?

(1) TypeScript end-to-end for type safety. (2) Self-hosted Judge0 instead of RapidAPI dependency. (3) Refresh tokens for longer sessions. (4) Streaming AI responses via SSE. (5) WebSocket auth from day one. (6) PostgreSQL for referential integrity (user↔submission foreign keys). (7) Cursor-based pagination instead of skip/limit. (8) Event sourcing for submission state changes. (9) Container orchestration (Docker + K8s) instead of Render. (10) Tests from the start — TDD.
