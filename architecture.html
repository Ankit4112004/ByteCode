Section 04

Middleware Pipeline

Every HTTP request passes through this chain. Each layer is fail-open where possible — Redis down = skip check, don't crash.

Request Lifecycle
flowchart LR REQ["🌐 Request"] --> CORS["CORS"] CORS --> JSON["express.json()"] JSON --> COOKIE["cookieParser()"] COOKIE --> ROUTE["Route Match"] ROUTE --> RL{"Rate Limit?"} RL -->|"Yes"| RLCHECK["⏱️ Redis ZSET\nSliding Window\n→ 429 if over"] RL -->|"No"| AUTHQ RLCHECK --> AUTHQ{"Auth?"} AUTHQ -->|"Yes"| AUTHMW["🔐 JWT Verify\n+ Role Check\n+ Redis Blocklist"] AUTHQ -->|"No"| CTRL AUTHMW --> IQ{"Idempotency?"} IQ -->|"Key Present"| IC["🔑 Redis Lookup\n→ Replay or Wrap"] IQ -->|"No Key"| CTRL IC --> CTRL["⚡ Controller"]
MW 1

🛡️ Rate Limiter

Redis sorted set per key. True sliding window — no burst-at-boundary issue. Factory pattern: createRateLimiter({ windowMs, max, keyPrefix, by }). Login: 8/min by IP. Submit: 10/min by user. Run: 20/min by user.

MW 2

🔐 Auth Middleware

Factory pattern: createAuthMiddleware(role?). Extracts JWT from httpOnly cookie → verifies → checks role (if admin) → loads user from MongoDB → checks Redis token blocklist. Fail-open on Redis.

MW 3

🔑 Idempotency

Client sends Idempotency-Key header. If already processed (Redis hit), replays cached response. Otherwise wraps res.json() to cache on success. TTL: 24 hours. Prevents duplicate submissions from double-clicks.

Authentication Flow

Stateless JWT auth with httpOnly cookies and a Redis token blocklist for immediate logout revocation.

Sequence Diagram
sequenceDiagram participant B as 🌐 Browser participant API as ⚡ Express API participant DB as 🍃 MongoDB participant R as ⚡ Redis Note over B,R: Registration B->>API: POST /user/register API->>API: Rate Limit (5/min per IP) API->>API: validate() + bcrypt.hash() API->>DB: User.create() API->>API: jwt.sign({_id, email, role}, 1h) API->>B: 201 + Set-Cookie: token=JWT Note over B,R: Login B->>API: POST /user/login API->>API: Rate Limit (8/min per IP) API->>DB: User.findOne({emailId}) API->>API: bcrypt.compare() API->>API: jwt.sign(...) API->>B: 201 + Set-Cookie: token=JWT Note over B,R: Session Check (page load) B->>API: GET /user/check (cookie auto-sent) API->>API: Auth MW (verify + blocklist) API->>B: 200 {user} or 401 Note over B,R: Logout B->>API: POST /user/logout API->>API: jwt.decode(token) API->>R: SET token:{jwt} BLOCKED EXPIREAT jwt.exp API->>B: Set-Cookie: token="" (maxAge=0)
ℹ️ Key Design Decision
The JWT is self-contained (no server-side session). On logout, the token is added to a Redis blocklist keyed by token:{jwt} with TTL matching the JWT's expiry. If Redis is down, the check is skipped (fail-open) — the JWT's built-in 1-hour expiry still limits the window.

Code Submission Flow

The core architectural showpiece — a fault-tolerant, asynchronous pipeline. The web tier never blocks on the slow external judge.

Async Pipeline Sequence
sequenceDiagram participant B as 🌐 Browser participant API as ⚡ Express API participant DB as 🍃 MongoDB participant Q as 📦 BullMQ Queue participant W as ⚙️ Worker participant CB as 🛡️ Circuit Breaker participant J as ⚖️ Judge0 participant LB as 🏆 Leaderboard (ZSET) participant WS as 🔌 Socket.io B->>API: POST /submission/submit/:id + Idempotency-Key API->>API: userMW → submitLimiter → idempotency API->>DB: Submission.create({status: 'pending'}) API->>DB: Problem $inc totalSubmissions API->>API: cacheDel('problems:all') API->>Q: enqueueSubmission({submissionId, userId}) API->>B: 202 Accepted {submissionId} Note over Q,W: Async Processing Q-->>W: Job dequeued (max 5 concurrent) W->>DB: Load Submission + Problem W->>CB: breaker.fire(batch) CB->>J: POST /submissions/batch J-->>CB: tokens[] CB->>J: GET /submissions/batch (poll ~1s) J-->>CB: results[] Note over W,LB: Saga Steps W->>DB: submission.save(verdict) alt Accepted + First Solve W->>DB: User.$addToSet(problemSolved) W->>LB: ZINCRBY global (weighted) end W->>LB: ZADD LT problem:{pid} (best runtime) W-->>WS: QueueEvents → completed WS-->>B: emit('submission:result', verdict) Note over W,B: Failure Path alt Circuit Breaker Open W--xCB: UnrecoverableError (skip retry) else Judge0 Error W->>W: BullMQ retries 3x (exp backoff) end W->>DB: submission.status = 'error' WS-->>B: emit('submission:result', {error})
💡 Back-Pressure
Worker concurrency: 5 caps simultaneous Judge0 calls. A burst of 100 users enqueues 100 jobs, but only 5 hit the external API at once — protecting the RapidAPI quota.
⚠️ Saga / Compensating Transaction
If evaluation fails partway, the submission is marked status: 'error' with an error message instead of remaining stuck on 'pending'. This prevents phantom "judging..." states in the UI.

Section 08

Cache-Aside Pattern

Redis caches problem data with a 5-minute TTL. Writes invalidate relevant keys. All cache ops are fail-safe.

Cache Flow
flowchart TD REQ["GET /problem/..."] --> HIT{"Redis\ncache hit?"} HIT -->|"HIT ✅"| RET1["Return cached JSON\n(TTL: 5 min)"] HIT -->|"MISS / Redis down"| DB["Query MongoDB"] DB --> WRITE["cacheSet(key, data, 300)"] WRITE --> RET2["Return DB result"] MUTATION["Problem Create /\nUpdate / Delete /\nNew Submission"] --> INV["cacheDel(\n'problems:all',\n'problem:id')"] style RET1 fill:#166534,color:#fff style INV fill:#991b1b,color:#fff
💡 Fail-Safe
If Redis is down: cacheGet returns null (miss), cacheSet and cacheDel silently skip. The app degrades to direct MongoDB reads — never crashes.

ℹ️ Process Decoupling
The worker may run as a separate process (or even on a different machine). It communicates results back through BullMQ's QueueEvents (Redis Pub/Sub under the hood), not through direct function calls. This decouples the worker from the web tier.

Section 18

Resilience & Fault Tolerance

How the system degrades gracefully when dependencies fail. MongoDB is the only hard dependency.

⚡ What if Redis goes down?

  • Cache → miss, read directly from MongoDB
  • Rate limiter → skipped, all requests allowed
  • Token blocklist → skipped, JWT expiry still works
  • Idempotency → skipped, normal processing
  • Leaderboard → returns empty/fallback
  • BullMQ → submissions won't process until recovery

⚖️ What if Judge0 goes down?

  • Circuit breaker OPENS after 50% failure (5+ calls)
  • Run requests → instant 503 response
  • Submissions → UnrecoverableError, skip BullMQ retries
  • User notified via Socket.io error event
  • Breaker HALF-OPENS after 30s to probe recovery

🍃 What if MongoDB goes down?

  • Server startup fails loudly (intentional)
  • All API requests return 500
  • Better to fail loudly than serve broken data
  • No graceful degradation — this is the source of truth
🔴 Critical Dependency
MongoDB is the only hard dependency. Redis and Judge0 both have fail-open / graceful degradation paths. If MongoDB is unreachable at startup, the server intentionally refuses to boot.
